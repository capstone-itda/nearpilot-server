# 펌웨어 spec의 실행 완료와 명령 기록 항목

- 관련 요구사항: FR-06, FR-07, NFR-10, NFR-14다.
- 근거: architecture.md §5 MQTT 3~5·7절이다.

## 지킬 계약

물리 완료를 증명한 기능만 `succeeded`로 보고한다.
실행 실패를 확인하면 `failed`다. 실행 여부나 완료 여부를 증명하지 못하면 `unknown`이다.
PUBACK, `accepted`, `running`과 제어 신호 송출은 물리 완료의 근거가 아니다.
IR 무드등의 관측 근거가 없으면 `light_on=null`이다.

기기는 접수 기록을 구동 전에 보존한다.
같은 `command_id`로 재접속·재부팅 뒤 다시 구동하지 않는다.
재시작 뒤 완료를 증명하지 못하면 `unknown`을 보고하고 자동으로 구동을 재개하지 않는다.

## spec에서 정할 내용

| 항목 | 담당자가 기록할 내용 |
|---|---|
| 완료 관측 | 사물함 `open`, 조명·스피커 `on`·`off`의 실제 완료 조건과 관측 수단이다 |
| 오류 검출 | 완료 관측의 이상 검출 범위와 확인 불가를 식별하는 방법이다 |
| 기록 저장 | 접수·진행·결과 기록의 저장 매체와 원자적 저장 방법이다 |
| 재시작 복원 | 기존 명령과 결과를 읽고 중복 구동을 막는 방법이다 |

관측 수단, 저장 매체와 실측하지 않은 센서 정확도는 아직 정하지 않았다.
담당자는 내부 선택을 구현 spec의 결정 절에 기록한다.
스피커의 새 보고 필드는 현재 계약에서 확정하지 않았다. 펌웨어 spec만으로 MQTT 필드를 추가하지 않는다.
완료를 증명하지 못한 기능을 가상 성공으로 대체하지 않는다.

## spec에 담을 검증

1. 제어 신호 송출과 실제 완료를 구분하는지 확인한다.
2. 접수 기록을 저장한 뒤에만 구동을 시작하는지 확인한다.
3. 명령 도중과 완료 직전에 전원을 차단하고 복원 결과를 확인한다.
4. 결과 저장 실패와 재시작 뒤 결과 불명을 `unknown`으로 보고하는지 확인한다.
5. 같은 명령의 재전송과 재부팅 뒤에도 다시 구동하지 않는지 확인한다.
6. 현재 계약의 결과 사건 ID와 재전송 내용을 보존하는지 확인한다.

반납 검사의 근거는 [반납 근거 항목](criteria.md)을 따른다.

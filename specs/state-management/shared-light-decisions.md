# 공용 조명의 선행 계약 이슈 초안

이 문서는 담당자에게 넘기는 초안이다. 팀 결정이 아니며 이슈를 생성하지 않았다.

## 초안 1: 서버가 시작하는 꺼짐 명령

### 질문
방문자 요청이 없는 이탈 꺼짐의 식별과 저장을 어떤 공동 계약으로 연결하는가?

### 맥락
- 관련 영역: CORE 상태 관리, 판정, DB, IOT다.
- 관련 요구사항: FR-20, FR-06, FR-19다.
- 입력: 유지 대상자가 없는 공용 조명과 현재 기기 연결이다.
- 출력: 식별하고 저장한 `off` 명령이다.
- 바뀌는 상태: 명령 진행 상태와 실행 결과다.
- 약속: 전송 직전에 유지 대상자와 현재 기기 상태를 다시 확인한다.
- 지금 정해야 하는 이유: `ExecutionContext`와 `link_command`는 방문자 요청의 내부 ID를 요구한다.

### 선택지
- A. 서버 내부 요청을 식별하는 공동 모델과 DB 저장 경로를 추가한다.
- B. 방문자 요청과 별개인 내부 명령 저장 접점을 제공한다.

### 제안
가짜 방문자 계정을 만들지 않는다. 명령 식별과 기기별 잠금의 전송 직전 범위를 함께 정한다.

## 초안 2: 이탈 꺼짐의 활성화

### 질문
실제 꺼짐 경로의 검증 뒤 이탈 꺼짐을 어떤 방법으로 활성화하는가?

### 맥락
- 관련 영역: CORE 상태 관리와 서버 조립이다.
- 관련 요구사항: FR-20, NFR-12다.
- 입력: 검증한 내부 꺼짐 경로다.
- 출력: 활성화한 이탈 꺼짐이다.
- 바뀌는 상태: 서버 운영 설정 또는 조립이다.
- 약속: 후보 반환만으로 자동 꺼짐을 활성화하지 않는다.
- 지금 정해야 하는 이유: spec은 검증 뒤 활성화를 요구하지만 방법은 미결이다.

### 선택지
- A. 검증한 실행 경로를 서버 조립에서 연결한다.
- B. 공용 설정에 활성화 값을 추가한다.

### 제안
새 공용 설정이 필요하지 않으면 A를 제안한다. 조립 담당과 실제 검증 범위를 먼저 정한다.

## 초안 3: 유지 대상자의 사용 권한

### 질문
횟수형 승인 소진 뒤 유지 대상자의 사용 권한을 어떤 계약으로 확인하는가?

### 맥락
- 관련 영역: CORE 상태 관리, 정책, DB다.
- 관련 요구사항: FR-20, FR-14다.
- 입력: 켜기 요청에 성공한 계정과 현재 정책이다.
- 출력: 현재 조명을 유지할 권한이다.
- 바뀌는 상태: 메모리의 유지 대상자다.
- 약속: 유지 권한을 확인하면서 새 조작을 허가하거나 승인 사용분을 예약하지 않는다.
- 지금 정해야 하는 이유: `PolicyChecker.check`는 새 조작의 정책 검사다. `PolicyCheckResult`는 승인 횟수 소진도 거부 사유로 구분한다.

### 선택지
- A. 기존 정책 검사 결과를 유지 권한에 그대로 적용한다.
- B. 성공한 사용분과 현재 정책으로 유지 권한을 확인하는 별도 접점을 정한다.

### 제안
정책 담당과 뜻을 확인한다. 현재 단위 검증은 진행 중인 spec의 A 가정을 따른다.

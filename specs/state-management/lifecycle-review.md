# 상태 관리 spec의 결정 분류

- 대상 브랜치: `feat/core-lifecycle-specs`
- 상태: 검토 중. 이 문서는 팀 결정이나 담당자 승인을 대신하지 않는다.
- 근거: `AGENTS.md`, `docs/`, 진행 중인 spec, 현재 `shared` 계약이다.
- 계약을 바꾸는 이슈와 PR은 생성하지 않았다.

## 1. 팀 결정이 필요한 항목

| 항목 | 결정할 질문 | 영향받는 spec |
|---|---|---|
| 미전송 취소 사유 | 예약 만료, 연결 없음, IOT의 미전송 증명을 어떤 `ReasonCode`로 전달하는가? | `core-execution`, `core-restore` |
| 실행 중단 사유 전달 | 재검사 외 사유를 `ExecutionResult`로 어떻게 전달하는가? | `core-execution` |
| 서버의 꺼짐 명령 | FR-20에 정한 CORE 내부 이탈 처리의 명령 식별·저장 경로를 어떻게 연결하는가? 방문자 접근 승인을 다시 받는 기능은 추가하지 않는다 | `core-shared-light`, `core-execution` |
| 이탈 꺼짐 활성화 | 검증 뒤 활성화하는 방법을 구현 때 정한다. 새 공용 설정이 필요할 때만 계약 변경을 논의한다 | `core-shared-light` |
| 장소 소유권 조회 | 복구 조회·승인에서 어떤 공동 접점으로 장소 소유자를 확인하는가? | `core-fault-recovery` |
| 복구 안전 근거 | 점유 세션이 없거나 종료된 기기의 검사 기준과 물리 상태 동기화 근거는 무엇인가? | `core-fault-recovery` |
| 판정의 복원 상태 조회 | 판정이 기기별 복원 상태를 어떤 접점으로 확인하는가? | `core-restore` |
| IOT 담당 문서 불일치 | architecture의 담당 표와 IOT 담당 미결 문구를 어떻게 일치시키는가? | IOT spec 3개 |
| CORE 내부 담당 배정 | `NodeEventSink`의 전체 구현과 `CoreService` 조립을 누가 맡는가? | `core-node-events`, `core-release` |
| 서버 시작과 API 담당 | 실행 진입점, 복원·구독·요청 수신의 조립과 관리 REST를 누가 맡는가? | `iot-mqtt-gateway`, `core-restore`, `core-fault-recovery` |
| 반납 검사 외부 계약 | 검사 기준의 내용·버전, 필수 `evidence`, 검사 ID 충돌 보고 형식은 무엇인가? | `core-release`, IOT spec |
| 실제 기기 검증 | 펌웨어 담당과 센서·완료 근거의 검증을 어떻게 배정하는가? | `iot-node-sim`, `iot-mqtt-gateway` |

위 질문은 팀 논의용 항목이다. 새 코드 값이나 접점을 이 문서에서 확정하지 않는다.
공동 계약의 변경은 관련 담당과 맞춘 뒤 반영한다. 기존 계약으로 가능한 구현과 fake 검증은 먼저 진행할 수 있다.
미연결 경로는 남은 작업으로 기록한다. fake 검증과 실제 연결 완료를 구분한다.

- 담당자 지시: 실제 기기의 시각 동기화와 허용 오차는 근접 추정 담당에게 맡긴다. 이 검토에서 수치·방식·담당 계약을 추가로 결정하거나 수정하지 않는다.

## 2. 다른 담당과 합의하거나 계약을 확인할 항목

| 항목 | 상대 | 처리 |
|---|---|---|
| `settlement_digest` 직렬화·해시 | DB 담당 | architecture가 두 담당의 spec 합의에 맡겼다. 단독 결정은 아니다. 기존 계약을 바꾸지 않으면 팀 전체 결정까지 요구하지 않는다 |
| 명령 미연결 예약 취소 | DB 담당 | `cancel_not_sent(expected=PENDING)`의 명령 부재 처리를 확인한다. 공동 계약을 보완해야 하면 팀 결정으로 넘긴다 |
| 정상 운영 중 예약 시각 확보 | 판정·DB 담당 | 인계 전 예약도 포함하여 시각·대상을 확보할 기존 경로를 확인한다. 새 인계 필드나 조회 접점이 필요하면 팀 결정이다 |
| 유지 대상자 권한 검사 | 정책 담당 | 기존 `PolicyChecker.check()`를 유지 권한 판단에 쓸 수 있는지 확인한다. 새 조작 허가와 유지 권한의 뜻을 바꿔야 하면 팀 결정이다 |

## 3. 담당자가 단독으로 정할 수 있는 항목

| 항목 | 선택 범위 | 현재 처리 |
|---|---|---|
| `rental_due_at`의 성공 시각 | 기기 결과의 `occurred_at` 또는 서버 결과 확정 시각 | `core-execution` 6절에 선택 대기로 명시했다. 재시도에도 같은 값을 유지해야 한다 |
| 점유 중 발표 변경의 추가 격리 | 신뢰 되돌림·점유 보존 위에 CORE 격리를 추가할지 결정 | `core-node-events` 6절에 선택 대기로 명시했다. DB의 저장 계약 변경은 포함하지 않는다 |
| 내부 모듈과 타이머 | 상태 관리 안의 함수 배치, 만료 감시 방식, 주입 방식 | 외부 입력·출력·타이밍과 공용 설정을 바꾸지 않는 범위에서 정한다 |
| spec 분할과 구현 순서 | 상태 관리 범위 안에서 공통 기능을 먼저 분리하거나 선행 의존을 명시 | 역방향 의존을 spec에 기록했다. 재분할과 내부 접점은 선택 대기다 |
| 브랜치 구성 | 검토용 묶음을 유지하고 구현 때 각 `feat/{계층}-{요약}`으로 분리 | 현재 브랜치는 유지했다. 브랜치 형식 검사 통과가 spec별 워크플로우 준수를 대신하지 않는다 |

6절의 선택 대기는 확정된 결정이 아니다. 담당자가 고른 뒤 결정과 이유로 바꾼다.

## 4. 기존 계약에 맞춰 바로 보완한 항목

| 항목 | 반영 |
|---|---|
| 명령 연결 전 중단된 예약 | 복원 표에 요청·예약 시각·명령 없는 공용형 사용분을 추가했다. 명령 부재를 완료로 취급하지 않는다 |
| 격리 성공 뒤 복구 건 저장 실패 | 재인계에서 복구 건 저장을 확인하고 같은 ID로 재시도하도록 보완했다. 재시작 중 누락 보완도 포함했다 |
| 정상 운영 중 예약 대기 만료 | `core-execution`에 책임과 예약 시각 기준, 전송 시작과의 경합, 테스트를 추가했다 |
| 시뮬레이터용 스키마 방향 | 명령·검사 요청 파싱과 기기 보고 직렬화를 추가했다. 기기의 중복 명령 우선 검사 순서를 보존했다 |
| 부분 구현과 완료의 혼동 | 임시 `not_sent`, 복구 틀, 기록용 꺼짐 콜백을 전체 기능 완료로 취급하는 문구를 고쳤다 |

위 수정은 새 팀 결정을 만들지 않는다. 사유 코드와 공동 접점이 필요한 부분은 1·2절의 선행 조건을 따른다.

## 5. 구현하면서 확인할 제안

- 자동 꺼짐 동작은 FR-20에 이미 정해져 있다. 모든 유지 대상자의 미수신·유예가 끝나면 CORE 상태 관리가 내부 처리로 `off`를 요청한다.
- 방문자 요청의 접근 승인이나 근접 판정을 자동 꺼짐에 다시 적용하지 않는 방향을 제안한다. 전송 직전 유지 대상자, 현재 연결, 온라인, 장애, 미완료 명령과 복원 상태는 확인한다.
- 내부 꺼짐 명령의 식별·저장만 DB 담당과 맞춘다. 방문자 계정을 가짜로 만들지 않고, 기존 MQTT `off` 계약을 사용한다.
- 펌웨어 배정 전에는 architecture의 MQTT v1 시뮬레이터 기준으로 실행·반납 흐름을 개발하고 시험한다. 실제 센서로 같은 근거를 제공할 수 있는지는 펌웨어 배정 뒤 검증한다.
- 복구 검사도 시뮬레이터 기준을 재사용하는 방향을 제안한다. 세션이 없는 경우의 기준 출처와 복구용 검사 결과 연결은 관련 계약을 먼저 맞춘다. 일반 `status`만으로 반납 안전을 확정하지 않는다.
- 장소 소유권은 DB가 기기와 장소를 연결해 소유 계정 일치 여부를 반환하는 접점을 제안한다. API는 인증 계정을 넘기고 CORE가 조회·승인마다 검사한다.
- 복원 상태는 상태 관리가 판정에 기기별 실행 가능 여부를 제공하는 최소 접점을 제안한다. 판정은 후보 처리에 쓰고 상태 관리는 전송 직전에도 검사한다.
- 모듈·타이머·직렬화의 세부는 구현할 때 정하고 spec을 갱신한다. 코드가 필요한 시점에 관련 담당과 계약을 맞춘다.
- 중복 실행 금지, 타인 핸들 거부, 불명 결과의 사용분 보존, 안전 확인 후 종료는 첫 구현부터 시험한다.

이 절은 추천안이다. 공동 모델의 함수나 필드, 복구 기준을 확정하지 않는다.

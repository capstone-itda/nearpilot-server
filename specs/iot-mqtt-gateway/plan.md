# IOT 전체 구현 계획

기존 spec 하나로는 작업 경계가 너무 넓다. MQTT 형식·연결·보고·명령·시뮬레이터를 다섯 spec으로 나눈다.
각 spec은 구현 전 초안이며 책임별 구현·검증 경계를 다룬다.
담당자는 2026-10-15에 다섯 spec을 하나의 검토용 draft PR로 올리도록 지시했다.

## 1. 분할 결과

| 순서 | spec | 구현 브랜치 | 완료 조건 |
|---|---|---|---|
| 1 | [메시지 형식](../iot-messages/spec.md) | `feat/iot-messages` | 일곱 토픽의 v1 본문과 shared 모델을 검증·변환한다 |
| 2 | [게이트웨이 연결](spec.md) | `feat/iot-mqtt-gateway` | 연결·재구독·접근 제어와 구독 준비를 검증한다 |
| 3 | [보고 검증·재인계](../iot-event-delivery/spec.md) | `feat/iot-event-delivery` | 현재 연결·최신성·중복을 검사하고 CORE 인계를 재시도한다 |
| 4 | [명령·검사 요청](../iot-command-gateway/spec.md) | `feat/iot-command-gateway` | 전송 결과를 구분하고 늦은 결과와 비동기 검사를 연결한다 |
| 5 | [기기 시뮬레이터](../iot-node-simulator/spec.md) | `feat/iot-node-simulator` | 명령 기록·구동 직렬화·재시작·반납 검사를 실제 MQTT로 재현한다 |

분할은 담당자가 승인한 책임 분리를 따른다. 시뮬레이터는 메시지 형식과 브로커 설정 뒤 먼저 만들 수 있다.
IOT 전체 연결 검증은 보고 검증과 명령 대기를 모두 구현한 뒤 실행한다.

## 2. 고치는 경로의 분담

| 경로 | 맡는 spec |
|---|---|
| `server/src/nearpilot/iot/messages/` | 메시지 형식 |
| `server/src/nearpilot/iot/mqtt/`의 연결·접속 설정·조립 | 게이트웨이 연결 |
| 같은 폴더의 보고 검증·현재 연결·재인계 | 보고 검증·재인계 |
| 같은 폴더의 명령 대기·검사 요청 | 명령·검사 요청 |
| `server/config/`의 Mosquitto 설정과 접근 제어 예시 | 게이트웨이 연결 |
| `server/tools/node_sim/` | 기기 시뮬레이터 |
| `server/tests/iot/` | 각 spec의 같은 책임을 검증하는 테스트 |

같은 `mqtt/` 폴더를 쓰지만 모듈의 책임을 겹치지 않는다. 후속 spec은 선행 모듈을 사용한다.
서버 진입점·CORE 조립은 #88의 별도 작업이다. 여러 계층의 검증은 `server/tests/integration/`에 둔다.

## 3. 요구사항의 전체 대응

| 요구사항 | 구현할 책임 |
|---|---|
| FR-04 | 발표의 형식 변환, retained 발견과 현재 연결의 분리, 재접속 발표 |
| FR-05 | RSSI 일괄 검증·비콘별 인계·메타데이터 보존·시뮬레이터 보고 |
| FR-06 | CORE 명령만 발행, ID 보존, 기기 영속 중복 방지와 구동 중 거부 |
| FR-07 | 물리 관측·결과 검증, 미전송·불명 구분, 재인계·늦은 결과·완료 근거 |
| FR-13 | 신선한 실시간 상태로 현재 연결 확인, 과거 관측의 현재 판정 사용 금지 |
| FR-20 | 검사 요청·결과 연결, §4 v1 근거, 확인 불능과 CORE의 종료 결정 |
| NFR-08 | 기기별 자격정보·토픽 접근 제어·송신 정보 최소화·비밀값 없는 로그 |
| NFR-10 | 여덟 가상 기기와 두 장소, 실제 센서 능력과 가상 관측의 구분 |
| NFR-11 | MQTT 3.1.1과 일곱 토픽의 QoS·retain |
| NFR-12 | 독립 AP의 Mosquitto와 외부 서비스 없는 실행 |
| 지표 8의 수신 데이터 | 운영과 같은 RSSI 검증·인계 경로. IOT에는 수집 회차·라벨을 넣지 않는다 |

기기 신뢰·등록 비콘 저장·온라인 시각의 저장은 CORE·DB가 맡는다.
실행 허가·점유·반납 종료·장애 복구는 CORE가 맡는다. IOT는 그 결정을 바꾸지 않는다.

## 5. 구현 전에 남은 선택

자세한 선택지는 [contract-review.md](contract-review.md)에 있다. 이번에 합의한 #140~#143과 구분한다.

| 사안 | 막는 spec | 추천 |
|---|---|---|
| S1 상태 보고의 허용 나이·연결 전환 동률 | 보고 검증·재인계 | 전용 최신성 기준과 현재 연결 유지 규칙을 확정한다 |
| S2 인증 주체 검증의 책임 | 게이트웨이 연결 | 브로커가 계정별 토픽 접근을 강제하고 IOT가 토픽·본문을 대조한다 |
| S3 접속 설정·시작·종료·구독 준비 접점과 시간 값 | 게이트웨이 연결·명령 조립 | IOT가 연결·구독을 관리하고 SUBACK까지 확인한다 |
| S4 재인계 용량·주기·포화 동작 | 보고 검증·재인계·명령 조립 | 결과를 버리지 않는 보존 규칙과 신규 명령 접수 제한을 정한다 |
| 시뮬레이터 명령 기록 저장 방식 | 기기 시뮬레이터 | 기기별 SQLite 파일을 쓴다 |

수치와 새 계층 간 접점은 임의로 확정하지 않는다. 결정이 필요한 부분은 각 spec의 가정 절에도 표시한다.
형식 변환과 이미 확정한 MQTT 규칙은 미결과 독립적으로 구현할 수 있다.

## 6. 브랜치와 검증

- 현재 브랜치의 다섯 spec을 한 draft PR에서 검토한다. 표의 구현 브랜치는 후속 구현의 계획이다.
- 각 feat PR에는 그 spec과 구현을 함께 넣는다. 계획만 있는 spec을 별도 feat PR로 main에 넣지 않는다.
- 완료한 앞 작업은 후속 작업의 의존성이다. 열린 PR을 이어 쓸 때 고유 커밋만 옮긴다.
- 이번 문서 검증은 최신 main의 기존 전체 `pytest` 1,495개 통과, 1개 예상 실패다.
- 표의 IOT 테스트는 아직 작성하지 않았다. 기존 테스트 통과를 새 IOT 구현 완료로 표시하지 않는다.
- 구현 뒤 `server/`에서 작업 범위의 IOT 테스트와 전체 `pytest`를 확인한다.
- Mosquitto 접근 제어와 IOT 전체 연결은 실제 브로커와 CORE fake로 검증한다.
- 실제 기기는 시각 오차·센서 능력·동작별 완료 근거를 따로 검증한다.

# IOT 계약 검토와 남은 결정

이 문서는 남은 서버 계약과 내부 선택을 기록한다.
펌웨어 계약과 spec 작성 항목은 [별도 폴더](../firmware-contracts/README.md)에 있다.
담당자는 2026-10-15에 내부 책임 분리와 실행 중 메모리 재인계를 선택했다.
전체 분할은 [plan.md](plan.md)에 있다.
계약의 근거는 이 브랜치의 `docs/`와 기존 spec이다. 닫힌 이슈 토론을 구현 근거로 쓰지 않는다.

## 1. 이미 정한 계약

| 계약 | 근거 | 이번 작업의 적용 |
|---|---|---|
| 프로토콜·토픽·QoS·retain·JSON 본문 | architecture.md §5 MQTT 1~3절 | 새 형식을 만들지 않는다 |
| 명령 중복 방지와 구동 중 거부 | FR-06, architecture.md §5 MQTT 4절 | 시뮬레이터도 재시작 뒤 명령 기록을 보존한다 |
| 결과 불명과 늦은 결과 | FR-07, architecture.md §4 "기기 보고의 인계" | 서버 결과와 기기 결과를 구분한다 |
| 반납 검사 요청과 CORE의 종료 결정 | FR-20, architecture.md §4 "반납 검사와 종료" | IOT는 결과를 기다리거나 점유를 해제하지 않는다 |
| 발표와 온라인 저장의 분리 | FR-04, FR-13, specs/state-management/core-node-events.md | retained 발표로 현재 연결을 바꾸지 않는다 |
| RSSI 저장과 수집 회차 | FR-05, architecture.md §4 "RSSI 수집 회차" | IOT는 수집 라벨을 받지 않는다 |
| 서버 조립 담당 | architecture.md §2, #88의 문서 반영 | 이번 작업은 게이트웨이와 시뮬레이터를 만든다 |

## 2. 펌웨어 계약의 참조

[펌웨어 계약 검수](../firmware-contracts/README.md)에 현재 계약과 펌웨어 spec에서 정할 내부 선택·검증 항목을 모았다.
게이트웨이와 시뮬레이터는 이 브랜치의 docs에 있는 MQTT v1을 따른다.
실제 기기의 미측정 수치와 새 보고 형식은 이 문서에서 확정하지 않는다.

## 3. 서버 계약의 결정 초안

다음 사안은 펌웨어 담당에게만 맡길 수 없다. 서버 조립·CORE·공용 설정과 닿는다.
아래 서버 사안은 아직 이슈로 발행하지 않은 선택지다. 펌웨어 내부 선택과 구분한다.

### S1. 상태 보고의 최신성

#### 질문

`status`의 허용 나이와 연결 전환의 동률을 어떤 규칙으로 검사하는가?

#### 맥락

- 관련 영역: IOT, 상태 관리, shared 설정이다.
- 관련 요구사항: FR-07, FR-13이다.
- 입력: 현재 시각, `observed_at`, `sent_at`, 검증한 최대 시각 오차와 기기 연결 ID다.
- 출력: 현재 연결로 인정한 `NodeStatus` 또는 거부 기록이다.
- 바뀌는 상태: IOT의 현재 연결과 CORE가 저장하는 온라인 시각이다.
- 약속: architecture.md §5 MQTT 6절은 신선한 실시간 `status`만 현재 연결로 인정한다.
- 약속: RSSI와 반납 검사의 허용 나이는 명시했지만 `status`의 허용 나이는 명시하지 않았다.
- 약속: 서로 다른 연결에서 관측 시각이 같을 때의 선택도 명시하지 않았다.
- 지금 정해야 하는 이유: IOT와 CORE가 서로 다른 연결을 현재 연결로 볼 수 있다.

#### 선택지

- A: `online_ttl_sec`를 상태 관측의 허용 나이에도 쓴다. 새 공용 수치를 만들지 않는다.
- B: 별도 상태 관측 허용 나이를 만든다. 공용 설정 이름·범위·초기값을 먼저 정한다.
- 공통 제안: 연결 전환은 더 새로운 관측으로만 허용한다. 동률이면 현재 연결을 유지한다.
- 공통 제안: 관측 나이는 검증한 최대 시각 오차를 포함한다. 허용 오차 밖의 미래 관측은 거부한다.
- 공통 제안: 재인계 시각을 새 수신 시각으로 쓰지 않는다.

#### 제안

독립된 최신성 기준이 필요하면 B를 제안한다. 수치는 실제 보고 지연과 오차를 확인한 뒤 정한다.
첫 구현을 기존 수치로 제한하려면 A를 선택하고 문서에 같은 값을 쓰는 이유를 기록한다.
담당자가 선택하기 전에는 상태 최신성 검사를 완성했다고 표시하지 않는다.

### S2. 인증 주체와 기기 ID의 대조

#### 질문

기기 자격정보와 `node_id`의 일치는 브로커가 증명하는가, 게이트웨이가 별도 정보를 받는가?

#### 맥락

- 관련 영역: IOT, Mosquitto 설정과 서버 조립이다.
- 관련 요구사항: NFR-08, FR-06이다.
- 입력: 인증한 기기 계정, MQTT 토픽과 JSON 본문의 `node_id`다.
- 출력: 인증 주체와 일치하는 보고다.
- 바뀌는 상태: 게이트웨이가 신뢰하는 보고의 출처다. 기기 신뢰 상태의 부여와는 다르다.
- 약속: architecture.md §5 MQTT 1절은 서버가 자격정보·토픽·본문의 기기 ID를 대조하도록 한다.
- 약속: MQTT 3.1.1 구독 메시지는 발행자의 인증 계정을 전달하지 않는다.
- 지금 정해야 하는 이유: JSON에 계정 이름을 추가해도 인증 주체의 증명이 되지 않는다.

#### 선택지

- A: Mosquitto가 계정별 토픽 접근을 강제한다. 게이트웨이는 토픽과 본문을 대조한다.
- B: 인증한 발행자 정보를 게이트웨이에 전달하는 브로커 확장을 추가한다.

#### 제안

A를 제안한다. MQTT 본문과 현재 기기별 자격정보 계약을 유지할 수 있다.
기기별 발행·구독 권한과 서버 전용 권한을 명시한다. 기기 ID와 계정의 대응을 설정으로 관리한다.
브로커의 교차 기기 발행·읽기 차단을 실제 연결로 검증한다.
문서의 서버 검증 책임은 이 책임 분담으로 명확히 고친다.
근거는 [MQTT 3.1.1 §3.3.2](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html)와 [Mosquitto 접근 제어 문서](https://mosquitto.org/man/mosquitto-conf-5.html)다.

### S3. 게이트웨이와 서버 조립의 연결

#### 질문

서버 조립은 게이트웨이에 어떤 설정을 주입하고 언제 구독 준비가 끝났다고 보는가?

#### 맥락

- 관련 영역: IOT, #88의 서버 조립과 shared 설정이다.
- 관련 요구사항: FR-06, FR-07, FR-13, NFR-08, NFR-12다.
- 입력: 브로커 주소·포트·서버 계정·비밀번호 위치, CORE 인계 접점과 적용 설정이다.
- 출력: 구독 준비 확인과 시작·종료 실패다.
- 바뀌는 상태: 서버가 복원을 시작하고 신규 요청을 받을 수 있는지 여부다.
- 약속: architecture.md §2는 구독 뒤 재시작 복원을 실행하고 그 뒤 요청을 받도록 한다.
- 약속: `shared.Settings`에는 브로커 접속 설정과 시각 오차 설정이 없다.
- 약속: `NodeCommandGateway`와 `SafetyCheckGateway`에는 시작·종료·구독 준비 접점이 없다.
- 지금 정해야 하는 이유: 연결 성공만 확인하면 구독 전 복원과 결과 유실이 생길 수 있다.

#### 선택지

- A: IOT가 접속 설정과 `start`·`stop` 접점을 제공한다. `start`는 필요한 구독의 SUBACK까지 확인한다.
- B: 서버 조립이 Paho 연결·구독을 관리하고 IOT에 이미 연결한 전송 객체를 주입한다.

#### 제안

A를 제안한다. architecture.md가 IOT에 배정한 연결·구독 책임을 유지한다.
접속 설정은 IOT 내부 설정으로 두고 판정용 `Settings`와 구분한다.
비밀번호 원문을 문서와 로그에 넣지 않는다. 기기별 자격정보와 접근 제어는 별도 실행 설정으로 제공한다.
정상 종료는 새 발행 접수를 멈추고 대기 중 명령을 확실한 미전송으로 바꾸지 않는다.
시작 제한 시간·재접속 대기·종료 대기 수치는 미결이다. 코드 상수로 넣지 않는다.
이 연결 계약은 조립 담당과 확정한다. 이번 작업이 서버 진입점을 대신 만들지는 않는다.

### S4. 메모리 재인계의 용량과 재시도

#### 질문

메모리 재인계의 용량·재시도 주기·포화 동작을 어떻게 정하는가?

#### 맥락

- 관련 영역: IOT, CORE와 서버 운영 설정이다.
- 관련 요구사항: FR-05, FR-07, NFR-08이다.
- 입력: 검증을 마쳤지만 CORE가 받지 못한 보고다.
- 출력: 같은 사건의 재인계 또는 운영 실패 표시다.
- 바뀌는 상태: 인계를 기다리는 메모리와 새 보고의 수용 여부다.
- 약속: architecture.md §4는 인계 실패를 기록하고 다시 인계하도록 한다.
- 약속: 담당자는 첫 구현의 보장을 서버 실행 중으로 제한했다. 재시작 복원은 범위 밖이다.
- 지금 정해야 하는 이유: CORE가 오래 실패하면 무제한 메모리 증가 또는 결과 유실이 생긴다.

#### 선택지

- A: 종류별 보존 규칙과 용량을 정한다. 포화 때 새 물리 명령 접수를 막고 운영 실패를 알린다.
- B: 첫 개발에서는 용량 제한 없이 보존한다. 장기 실패에서 메모리 증가를 허용한다.

#### 제안

A를 제안한다. 실행 결과와 검사 결과를 조용히 버리지 않는 규칙을 먼저 정한다.
RSSI·상태의 합치기나 폐기는 CORE가 재인계에서 기대하는 시각·순번 계약과 함께 정한다.
용량·재시도 주기와 포화 해제 조건은 담당자 선택 뒤 운영 설정으로 기록한다.
이 사안은 메모리 재인계를 영속 저장으로 확대하는 제안이 아니다.
Paho의 자동 PUBACK는 CORE 저장 완료가 아니다. 재시작 보장을 문서에 추가하지 않는다.
기술 근거는 [Paho의 manual_ack 설명](https://eclipse.dev/paho/files/paho.mqtt.python/html/client.html)이다.

## 4. 내부 구현에서 남은 선택

- 시뮬레이터의 명령 기록 저장 방식은 아직 정하지 않았다.
- A안은 기기별 SQLite 파일이다. 접수 기록과 결과 갱신을 트랜잭션으로 보존한다.
- B안은 파일 기록이다. 접수와 결과 기록의 원자적 저장·손상 복원을 직접 정한다.
- A를 제안한다. 서버 DB와 분리한 시뮬레이터 전용 파일을 쓴다.
- 초기 구현은 명령 기록을 자동 삭제하지 않는다. 저장소가 가득 차면 새 구동을 허용하지 않는다.
- 저장 방식은 내부 선택이다. 담당자가 선택하면 spec의 결정 절에 옮긴다.

## 5. 기존 CORE 구현과 문서의 차이

`core/lifecycle/check_criteria.py`의 `evidence_valid()`는 `fault`·`unknown`의 필수 근거 검사를 생략한다.
architecture.md §4는 검사 항목이 하나라도 없는 결과를 유효하지 않은 결과로 본다.
IOT 보고 검증은 문서대로 불완전한 근거를 유효한 결과로 전달하지 않는다.
CORE를 직접 호출하는 경로는 더 느슨할 수 있다. 서버 전체 연결 전에 기존 반납·복구 spec의 fix에서 확인해야 한다.
이번 문서 PR은 CORE 동작을 바꾸지 않는다. `unknown`·`fault`의 근거 예외를 채택하려면 #143의 후속 계약이 필요하다.

## 6. 확인할 순서

spec 초안은 기존 회귀 테스트를 확인한 뒤 먼저 커밋한다. 아래 순서는 구현 착수의 선행 조건이다.

1. 담당자가 S1~S4와 시뮬레이터 저장 방식을 선택한다.
2. 팀 계약을 바꿔야 하는 선택은 별도 decision PR로 문서와 shared에 반영한다.
3. 담당자가 확정한 내부 선택을 spec의 결정 절에 기록한다.
4. `server/`에서 전체 `pytest`를 확인한다.
5. 구현 전에 확정한 spec 변경을 커밋한다.
6. plan.md의 다섯 feat 작업을 각 spec과 함께 구현한다.
7. 단위 테스트와 Mosquitto 계약 검증을 마친다.
8. 서버 조립 작업에서 CORE·DB를 연결한다.
9. 실제 기기는 [펌웨어 검수](../firmware-contracts/README.md)의 실제 기기 검증 근거를 확인한 뒤 연결한다.

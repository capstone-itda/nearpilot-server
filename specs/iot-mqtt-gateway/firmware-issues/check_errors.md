## 질문

검사 ID 충돌·미지원 기준·측정 불능을 기존 결과 형식에서 어떻게 구분하는가?

## 맥락

- 관련 영역: 펌웨어, IOT, 상태 관리, shared다.
- 관련 요구사항: FR-07, FR-20, NFR-04다.
- 입력: 같은 check_id의 다른 내용, 미지원 기준, 시각·연결 검증 실패, 센서 측정 실패다.
- 출력: safety_check_result 또는 검사 응답의 부재다.
- 바뀌는 상태: CORE의 확인 불능과 장애 격리 근거다. 기존 검사 결과는 보존한다.
- 약속: architecture.md §4는 같은 check_id의 다른 내용을 충돌로 거부하도록 한다.
- 약속: 같은 절은 충돌 보고 형식을 미결로 두고 현재 서버가 응답 기한 초과로 다루게 한다.
- 약속: 결과는 passed·not_ready·fault·unknown이다. 실행 결과의 RejectCode를 검사 결과에 쓰는 계약은 없다.
- 약속: evidence는 필수 항목마다 bool 값과 관측 시각을 요구한다. 측정 실패와 미지원 기준에서는 그 값을 만들 수 없다.
- 지금 정해야 하는 이유: 측정하지 않은 값을 false로 만들면 정상 not_ready와 확인 불능을 혼동한다. 충돌 결과를 기존 passed의 변경으로 보고해도 안 된다.
- 근거: docs/requirements.md FR-07과 docs/architecture.md §4 "반납 검사와 종료", §5 MQTT 3절이다.

## 선택지

### A. 첫 구현은 기존 확인 불능 경로를 유지하고 오류 보고 확장을 따로 계약한다
- 결과: 같은 check_id의 다른 내용은 실행하거나 기존 결과를 덮어쓰지 않는다. 서버는 현재 계약대로 응답 기한 초과로 다룬다.
- 결과: 기기는 만들 수 없는 bool 근거를 꾸미지 않는다. 서버는 불완전한 결과를 확인 불능으로 다룬다.
- 결과: 검증 가능한 fault 근거가 있으면 기존 fault 결과를 사용한다.
- 결과: 오류 코드, unknown·fault의 필수 근거 예외, 오류 사건 ID 규칙은 새 계약으로 따로 정한다.
- 결과: 서버·CORE·shared의 검증을 함께 바꾼 뒤 오류 보고를 활성화한다.

### B. 검사 거부 전용 결과를 지금 추가한다
- 결과: 검사 결과 상태, 오류 코드와 evidence 형식을 확장한다.
- 결과: MQTT·shared·CORE·DB가 함께 새 계약을 구현해야 한다.

## 제안

첫 구현에는 A를 제안한다. 기존 서버의 확인 불능 동작을 유지한다.
충돌을 passed·not_ready로 바꾸지 않는다. 미지원 기준을 통과로 보지 않는다.
오류 보고 확장은 이 이슈의 후속 decision PR에서 구체화한다.
펌웨어 담당 미정 상태에서도 서버·시뮬레이터의 보수적인 실패 동작은 검증할 수 있다.

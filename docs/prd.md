# NearPilot 서버 PRD

> 이 저장소의 **최상위 요구사항 문서**다. 개발 범위·필수 동작·인수 기준은 이 문서로 판단하고, 하위 설계와 충돌하면 이 문서를 우선한다. 구조·기술 선택·상세 스키마는 [아키텍처](./architecture.md)에서 관리한다. FR·NFR ID는 추적용이며, 요구사항 이해에 별도 원문을 요구하지 않는다.

## 1. 제품과 범위

NearPilot은 AI 호스트의 자연어 요청을 실제 주변 기기의 사용으로 연결하는 인증·판정 서버다. 전용 앱과 장소별 가입의 번거로움, 잘못된 기기 선택, 다중 사용자 간섭을 줄인다. **계정·비콘 관측·접근 정책·점유 상태를 서버가 결정론적으로 검사하고, 허가한 요청만 노드가 실행한다.** LLM이나 호스트 확인 UI는 허가의 근거가 아니다.

| 주체 | 역할과 서버 접점 |
|---|---|
| 방문자 | Android 앱으로 계정·비콘을 한 번 등록하고 백그라운드 송출. 장소별 등록 없이 AI 호스트로 조회·사용·해제 |
| 소유자·설치자 | 앱에서 접근 승인·거부, 대시보드에서 노드 신뢰·장소·정책 설정과 FAULT 복구 |
| AI 호스트 | Claude·ChatGPT·Gemini가 같은 MCP URL·도구를 사용. 토큰으로 연결하며 사용자 ID를 입력하거나 전달받지 않음 |
| ESP32 노드 | 기능 발표·RSSI·안전 상태·실행 결과를 MQTT로 보고하고 서버 명령을 실행 |

서버 범위는 MCP, 앱·대시보드 REST, 모니터링 WebSocket, MQTT 연동, 근접 추정, 정책·승인, 점유·해제, 기록·평가다. Android UI·ESP32 펌웨어·대시보드 프런트엔드는 별도 구현이며 서버는 연동 계약을 제공한다. iOS, 실제 잠금장치·고보안 출입문·게이트, 강한 단말 인증, LLM을 이용한 서버 판정은 범위 밖이다.

시연 환경은 ESP32 + NimBLE, 저전압 모형 사물함 3개(서보·리드 스위치), LED 조명 3개, 앵커 6개, 유효 반경 약 0.5 m다. 행사장 Wi-Fi에 의존하지 않는 독립 AP·핫스팟을 사용한다. 앱은 비콘 송출 상태를 표시하고 중단을 감지하며, 서버는 연속 미수신과 유예시간으로 일시 유실과 이탈을 구분한다. 고정 iBeacon은 복제 방지용 강한 인증 수단이 아니다 (FR-02, NFR-10·12·14).

## 2. 기능과 외부 계약

아래 기능은 필수이며 실시간 모니터링(FR-12B)은 일정 여유 시 구현한다. 서버는 `/mcp`에 MCP Streamable HTTP를 직접 제공하고 같은 프로세스에서 토큰 식별과 판정을 처리한다. 앱·대시보드는 HTTPS REST·WebSocket, 노드는 MQTT, 폰→노드는 BLE iBeacon을 사용한다 (FR-08, NFR-11).

| 기능 | 필수 동작 | ID |
|---|---|---|
| 계정·연결 | 계정–비콘 등록, 토큰 발급·검증. 다른 계정에 등록된 비콘 식별자와 토큰 없는/무효 호출은 거부 | FR-01·08 |
| 노드 발견 | 부팅 시 기능·점유 방식 발표 수신, 소유자가 장소 배치·신뢰 설정. 신뢰와 온라인 여부를 분리하고 미신뢰·오프라인·FAULT는 후보에서 제외 | FR-04·13 |
| 관측·실행 | 약 1초 단위 RSSI 보고와 상태·결과 수신. 서버가 허가한 명령만 전달하고 실행 결과를 확인 | FR-05~07 |
| 접근 정책·승인 | 장치별 정책 설정, 접근 요청, 승인 대기 목록, 권한 있는 소유자의 승인·거부. 승인 여부는 사용 시 서버가 검사 | FR-03·14 |
| 관리·모니터링 | 노드·정책·FAULT 복구 관리 API, 판정·후보 확률·상태 전이·감사 로그 스트림 | FR-12A·12B |
| 판정·근접 | 등록 비콘 대조, 관측 모델 + HMM 근접 추정, 비용 기반 재질문, 정해진 순서의 실행 허가 판정 | FR-15~18 |
| 점유·기록·할당 | 원자적 점유, 장치별 종료·해제, 핸들 소유권 검사, 재현 가능한 감사 기록, 전역 할당 | FR-19~23 |

### MCP 도구 6개 (FR-09~11·21)

| 도구 | 계약 |
|---|---|
| `find_available_devices` | 근접·신뢰·온라인·사용 가능·미점유 후보를 '조작 가능'과 '승인 필요'로 구분. 비공개 장치·점유 주체 비노출, 비콘 미수신이면 빈 목록 |
| `get_device_state` | 근접 검사 없이 장치 상태 조회. 공개 장치는 유효 토큰, 비공개 장치는 소유자 또는 현재 본인 사용 세션 권한 필요. 점유 주체 비노출 |
| `request_access` | 제한 장치에 대한 접근 승인 요청. 승인 요청 자체가 실행 허가는 아님 |
| `request_use` | `target_spec`, 동작, `request_id`로 사용 요청. 중복·근접·정책·점유 검사 후 실행 |
| `release_use` | 본인 `use_id`의 사용 종료 요청. 유효한 사용 권한과 장치의 해제 정책·안전 상태를 확인 |
| `get_use_status` | 근접 검사 없이 본인 세션·종료 이력 조회. 사용 권한이 만료돼도 이력 보존기간 내 조회 가능하며 타인 핸들은 거부 |

`target_spec`은 근접 지정(`nearest:locker`), 명시적 지정(`locker-1`), 허용 후보 중 배정(`any:locker`), 동작은 `open`·`on`·`off`를 지원한다. 명시적 지정도 근접 확률이 임계값 미만이면 실행하지 않고 이동을 안내한다. 재질문·승인 후 사용 재요청은 새 `request_id`를 사용하고 원래 요청/승인과 연결한다. 같은 요청의 전송 재시도는 기존 ID를 유지한다. 응답에는 판정·사유·장치 정보·본인 요청/사용 핸들을 담고 사용자 ID와 점유 주체는 제거한다.

접근 정책은 `open`(개방) / `restricted`(승인 필요)다. 승인은 **요청자·장치·동작·정책 버전**에 묶고 승인 권한 계정만 처리한다. 사물함은 기본 `one_time`으로 실행 후 소진, 조명은 `time_window`로 유효기간 내 반복 허용하며 횟수·유효시간을 장치별 설정한다. 거부·만료·정책 변경 시 재승인이 필요하고, 횟수 초과·다른 동작은 거부한다. 정책 변경은 진행 중 점유에 소급하지 않는다 (FR-03·14).

공개 범위 `public/private`는 승인 필요 여부와 별도로 관리한다. 비공개 장치는 주변 목록에서 숨기고, 과거 사용 이력은 해당 세션 기록의 조회만 허용한다. 접근 정책은 버전별 내용을 보존하며 운영 설정 버전과 분리한다. 운영 수치만 변경했다고 기존 승인을 무효화하지 않는다.

MQTT는 노드별 기능 발표(`announce`, retained), 관측(`rssi`), 상태(`status`), 실행 결과(`result`), 명령(`cmd`)을 사용한다. 서버는 외부 `(계정, request_id)`를 전역 고유 `internal_request_id`에 연결하고, 물리 명령마다 고유 `command_id`를 발급한다. 노드 명령·결과·중복 방지는 `command_id`로 연결한다. 노드별 자격정보를 검증하고 시간 초과·연결 끊김은 실행 성공으로 처리하지 않는다.

### 수치 설정과 변경 원칙

- 본문의 근접 임계값(0.95/0.75), 관측 주기(약 1초), 이탈 판단(10초+5초), 할당 대기(500ms)는 **초기 기본값**이다. 코드 상수로 분산하지 않고 이름·단위·허용 범위가 있는 설정으로 관리한다. 값이 없는 타임아웃 등은 §7의 미결로 유지한다.
- 설정은 서버 기본값과 필요한 장치 종류/장치별 재정의로 관리한다. 판정 한 건에는 동일한 설정 버전을 적용하고, 실제 적용 값과 버전을 감사 기록에 보존한다. 변경 시 값의 범위와 관련 시간값의 일관성을 검증한다.
- 초기 변경 방식은 설정 파일·DB 수정 후 재시작으로 한다. 관측 처리·보정·HMM은 교체 가능한 인터페이스로 분리하고 모델·설정 묶음을 보존한다.
- 새 기본값은 신규 요청·세션부터 적용한다. 기존 승인의 만료·횟수와 진행 중 세션의 종료 정책·만료 시각은 생성 당시 값으로 유지한다. 현재 신뢰·온라인·안전 상태 검사는 계속 적용하고, 접근 정책 버전 변경 시 재승인 규칙도 유지한다.
- 모델과 결합된 임계값은 검증셋으로 함께 검증한다. §6의 성능 목표·표본 수는 평가 기준이며 운영 설정과 별도로 버전 관리한다. 팀 합의로 수정할 수 있지만 한 평가 회차 안에서는 고정하고 변경 전후 결과를 구분한다.
- 서버 인가·소유권 검사·중복 실행 금지·안전 확인 후 해제는 수치 조정으로 완화하지 않는다. API·상태·식별자·DB 관계 변경은 호환성 및 데이터 이전 검토를 거친다.

## 3. 실행 허가 규칙

인증·입력 검증 후 다음 순서를 적용한다. **기본값은 거부**다. 공용형의 점유 검사 생략 외에는 호스트나 사용자 발화로 단계를 생략할 수 없다 (FR-15~18).

| 순서 | 검사와 결과 |
|---|---|
| ⓪ 중복 | `(계정, request_id)`와 정규화한 입력을 대조. 같으면 기존 결과·진행 상태 반환, 같은 키의 다른 입력은 충돌로 거부. 다른 계정의 결과는 반환하지 않음 |
| ① 비콘 | 토큰 계정의 등록 비콘이 해당 장소 앵커에서 최근 T초 이내 수신됐는지 검사. 원격 요청·관측 부재는 `DENY` |
| ② 후보 | 신뢰·온라인·요청 종류가 맞고 FAULT가 아닌 장치로 구성. 정책·점유 때문에 다른 물리적 대상이 선택되지 않도록 정책·점유 검사는 대상 확정 후 ④~⑥에서 수행 |
| ③ 근접 | 앵커별 RSSI에 관측 모델 + HMM을 적용해 사후확률 최대 장치를 선택. 설정 임계값(초기 사물함 0.95·조명 0.75) 미만이면 실행 없이 `ASK` |
| ④ 정책 | 장치 정책과 접근 승인을 검증. 승인이 필요하면 `NEED_APPROVAL`, 정책상 허용되지 않으면 `DENY` |
| ⑤ 장치 점유 | 배타적 장치가 이미 점유 중이면 장치 사유의 `BUSY` |
| ⑥ 사용자 점유 | 같은 `exclusive_group`에서 이미 다른 장치를 점유하면 사용자 사유의 `BUSY`. ⑤⑥ 검사와 예약 생성은 한 트랜잭션으로 처리 |

판정은 `OK`(허가), `BUSY`(장치/사용자 점유 충돌), `ASK`(재질문), `DENY`(거부), `NEED_APPROVAL`(승인 필요)다. 비허가 요청은 기기를 실행하거나 새 점유를 유지하지 않는다. **실행 직전 허가·근접·대상을 재검사**하고 자기 요청의 예약은 타인 점유로 간주하지 않는다. 공용 조명은 ⑤⑥과 점유 세션 생성을 건너뛰지만 승인 사용분은 원자적으로 확보한다. 실행 확인 전에는 호스트에 완료를 안내하지 않는다.

대표 흐름: `request_use(nearest:locker, open, request_id)` → 계정 식별·내부 ID 연결 → ⓪~⑥·승인 사용분 확보 → `RESERVED` → 실행 직전 재검사 → 노드에 `OK!(command_id)` → 실행 확인·승인 소진 → `ACTIVE`·`use_id` → 완료 안내. 근접 임계값 조정은 검증셋에서만 수행하고 시험셋 평가 전에 고정한다.

전역 할당(FR-23)은 **설정된 대기 구간(초기 500ms) 내 `any:locker` 요청**을 묶는다. 동일한 근접 임계값·정책·점유 조건을 만족한 허용쌍에서 **배정 수 최대화 → 비용 `−log(근접확률)` 합 최소화 → ID순**으로 1:1 배정한다. 근접 확신 부족은 `ASK`, 점유·경합으로 미배정되면 `BUSY`, 인증·정책 실패는 해당 판정을 유지한다. 실행 직전 재검사도 수행한다. 초기 0.95 기준에서는 사용자당 허용 후보가 최대 하나일 수 있어 충돌 조정 중심으로 동작하며, 배정 후 이동을 전제로 근접 조건을 완화하지 않는다.

## 4. 점유·해제·복구

- **원자성·멱등성:** SQLite 단일 쓰기 경로와 `BEGIN IMMEDIATE`로 장치·사용자 점유 확인 및 `RESERVED` 생성을 묶는다. 동시 요청·재전송에도 이중 점유와 중복 물리 실행을 방지해야 한다. 서버 기록과 노드의 중복 실행 방지 계약을 함께 정의한다 (FR-19, NFR-03).
- **승인 사용분:** 실행 전에 요청별 사용분을 원자적으로 예약하고 잔여 횟수에서 제외한다. 대여형은 점유 예약과 같은 트랜잭션에서 처리한다. 성공 확인 시 소진 확정, 재검사 실패 등 명령 미전송이 확실한 경우에만 자동 반환한다. 전송 후 결과 불명은 승인 사용분·점유를 보류하고 복구 후 실행 여부에 따라 정산한다.
- **장애·재전송:** 서버와 노드는 명령·처리 기록을 재시작 후에도 보존하고 같은 `command_id`를 다시 실행하지 않는다. 전송 시도 후 응답 유실·재시작으로 실행 여부가 불명확하면 새 명령으로 재시도하지 않고 FAULT 복구한다. 기록만으로 실행 여부를 확정하지 못하면 물리 상태 확인까지 신규 허가를 차단한다.
- **대여형 사물함:** 장치는 `AVAILABLE → RESERVED → ACTIVE → CLOSING → AVAILABLE`. 실행 확인 시 `ACTIVE`와 계정·장치·만료에 묶인 `use_id`를 발급한다. 점유 세션은 `RESERVED → ACTIVE → CLOSING → CLOSED`이며 종료 사유는 `release / leave / timeout / fault`다.
- **종료:** 명시 해제·대여 타임아웃·비콘 연속 미수신과 유예 만료(초기 **10초 미수신+5초 유예**) 시 `CLOSING`. `release_policy`의 안전 상태 확인 후 세션을 `CLOSED`, 장치를 `AVAILABLE`로 바꾼다. 그 전에는 다음 사용자에게 허가하지 않는다 (FR-20).
- **이탈 취소:** 유예 중 유효 비콘이 다시 수신되면 이탈 타이머를 초기화한다. 이미 `CLOSING`에 진입했으면 비콘 재수신만으로 `ACTIVE`로 되돌리지 않고 안전 확인·종료를 계속한다.
- **공용 조명:** 점유·`CLOSING` 없이 상태를 변경한다. 이탈 시 자동 꺼짐은 초기 비활성으로 두며, 다중 사용자 유지 기준을 정한 뒤 `release_policy`로 활성화한다.
- **실패·복구:** 어느 상태에서든 이상이 감지되면 장치를 `FAULT`로 격리·후보 제외한다. 무응답·센서 이상·안전 미확인 시 불명확한 점유 세션을 보존한다. 장치별 안전 확인 → 서버·물리 상태 동기화 → 소유자 승인 후에만 `AVAILABLE`로 복구하고 전 과정을 기록한다 (NFR-04).
- **소유권:** 조회·해제는 토큰 계정과 `use_id` 소유권을 대조한다. 만료된 사용 권한으로 추가 조작·해제할 수 없지만 본인 종료 이력은 보존기간 내 조회할 수 있다. 만료 후 안전 종료는 서버가 수행한다 (FR-21).

## 5. 데이터·보안·재현

| 보존 대상 | 필요한 정보·불변 조건 |
|---|---|
| 계정·비콘·장소 | 역할 `visitor/owner`, 토큰 해시 고유성, 활성 비콘과 계정 연결, `(uuid, major, minor)` 고유성, 장소 소유자 |
| 노드·장치 | 기능 `locker/light`, 점유 방식 `rental/shared`, 신뢰 `discovered/trusted/revoked`, 장소·상태·배타 그룹·해제 정책. 온라인은 `last_seen_at`과 TTL로 계산 |
| 정책·승인 | 공개 범위와 접근 모드, 정책 버전별 내용, 신청자·대상·승인 결과, 승인 사용분 예약·보류·소진 기록 |
| 요청·사용·명령 | 외부 `(계정, request_id)`·입력 요약, 내부 요청 ID·명령 ID, 계정·대상·동작·판정·사유·최대 확률·호스트, 세션·만료·종료 사유, 명령 전송·처리 기록. 대상 미확정이면 대상 ID는 NULL |
| 관측·감사 | 앵커·비콘·RSSI·프레임 시각·수집 라벨(장치 1~6 앞/none), 단계별 입력·결과, 후보 확률, 모델·보정·정책 버전, 임계값·관측 구간, 실행·종료·복구 |

판정은 내부 요청 ID로 외부 계정별 요청을 추적하고 동일한 모델·보정·정책·설정 값으로 재현한다. 내부 요청 행을 먼저 만든 후 단계 로그를 연결한다. 인증 실패 등 요청 행이 없는 사건은 별도 이벤트 ID와 NULL 요청 참조로 남긴다. 감사 테이블·JSONL을 보존하고 평가 표·그래프는 스크립트로 생성한다 (FR-22, NFR-13). 재현 시 물리 명령을 재전송하지 않는다. 데이터 관계는 아키텍처에 정의하며 테이블 수는 고정하지 않는다.

호스트·앱은 HTTPS와 토큰, 서버↔노드는 폐쇄망과 노드별 자격정보로 인증한다. 비콘 없는 토큰·타인 핸들·미신뢰 노드·유도된 타 장치 호출을 차단하고 기록한다. 사용자 ID는 LLM에 노출하지 않는다 (NFR-07·08). 관측·로그는 평가 후 계정 ID를 제거한 공개용 데이터셋으로 보존하고, 토큰 해시와 비콘 식별자는 프로젝트 종료 시 폐기한다.

## 6. 인수 기준

| # · 항목 | 측정 방법 | 통과 조건 |
|---|---|---|
| 1 · 기기 선택 | 동일 발화 100건 | 타 장치 동작 ≤ 2.5% (NFR-05) |
| 2 · 재질문 | 6개 위치 × 30회, 비용 비율별 곡선 | 같은 재질문률에서 오작동 감소, 오작동 0건 (NFR-06) |
| 3 · 점유·중복 | 동시 클라이언트 요청 2,000회·재전송 100회 | SQLite 잠금 오류 처리 후 이중 점유 0건, 동일 요청의 물리 실행 ≤ 1회 (NFR-03) |
| 4 · 다중 사용자 | 3명 동시 50회씩 | 타 사용자 기기 오동작 0건, 요청 기기 동작 성공 ≥ 95% (NFR-05) |
| 5 · 정책·발견·차단 | 미등록·무권한·1회/기간 승인·타인 핸들·미신뢰 각 30회 | 범위 밖 조작·미신뢰 후보 0건, 유효 승인 성공 ≥ 95% (NFR-07) |
| 6 · 종료·복구 | 장치별 명시 해제·이탈 유예·타임아웃·센서 장애 각 30회 | 정책과 다른 CLOSING·안전 미확인 후 다음 OK 0건, 복구 성공 ≥ 95% (NFR-04) |
| 7 · 지연·호환성 | 서버 판정 100회, 호스트별 동일 발화 50건 | 요청 수신→결과 반환 median ≤ 1초·p95 ≤ 2초, 발화→안내 median ≤ 3초·p95 ≤ 6초. 3종 호스트 판정·결과 일치 ≥ 98%, 호스트 교체 시 서버 변경 없음 (NFR-01·09) |
| 8 · 근접 모델 | 위치별 독립 수집 ≥ 5회, 회차 단위 60/20/20 분리, 단계별 제거 실험(ablation) | 정면 오선택 ≤ 5%, 10구간 ECE(확률 보정 오차) ≤ 0.05, 이동 후 대상 전환 ≤ 2초, 정지 시 대상 깜빡임 80% 감소 (NFR-02·06) |
| 9 · 전역 할당 | 3명·사물함 3대 위치·점유 조합 50세트 | 허용쌍만 배정, 중복 배정 0건, 기준 최대 배정 수와 그 안의 최적 비용 100% 일치 |

같은 수집 회차의 RSSI 프레임은 데이터 분할 간 섞지 않는다. 임계값은 검증셋에서만 선택하고 시험셋 확인 전에 고정한다. 지표 3은 부하 스크립트, 지표 9는 기준 최적해로 비교하며, 0건 결과에는 95% 신뢰구간 상한을 적는다. 입력·시나리오·버전·표본 수를 보존한다.

서버 범위의 FR마다 pytest 케이스를 둔다. 초기 호스트 연동은 `tools/list`와 무해한 도구 호출로 확인한다. 세 기기 분리·두 종류의 BUSY·자동 해제 후 재사용·호스트 교체의 대표 4장면을 50회 리허설하고 성공률·실패 원인을 기록한다.

아래는 측정·펌웨어 연동·보존 정책을 구체화할 잔여 항목이며, 수치는 §2에 따라 조정한다.

| 향후 조명 자동 꺼짐 | 활성화 전 다중 사용자 유지 기준·시간을 정의. 초기 비활성 구현은 이 결정에 의존하지 않음 |

## 1. 공통 규칙

### 1.1 범위와 지표 표기

요구사항의 "범위" 항목은 아래 값 중 하나다.

| 범위 | 뜻 |
|---|---|
| `서버` | 이 저장소가 구현한다. pytest로 검사한다. |
| `연동` | 앱, 기기, 호스트가 주체다. 서버는 계약의 상대편만 구현한다. |

- 서버와 기기는 폐쇄망 안의 시각원으로 동기화한다. 최대 시각 오차는 기기별 실측 뒤 배포 설정으로 관리한다 (#140 A안).
- 미결 — #140: 실제 기기의 동기화 방식, 재동기화 간격, 최대 시각 오차와 설정 이름이다. 검증 전 값은 미설정이다.
- 수치는 코드 상수로 흩어 쓰지 않는다. 수치는 이름, 단위, 허용 범위가 있는 설정으로 관리한다.
- 값을 정하지 않은 수치는 `미결`로 둔다.
- 설정은 서버 기본값과 재정의로 구성한다. 재정의는 기기 종류별 또는 기기별로 둘 수 있다.
- 판정 한 건에는 설정 버전 하나를 적용한다. 서버는 실제로 적용한 값과 버전을 감사 기록에 보존한다.
- 설정을 바꾸면 서버는 값의 범위와 관련 시간 값끼리의 일관성을 검증한다.
- 초기에는 설정 파일이나 DB를 고친 뒤 서버를 재시작해서 설정을 바꾼다.
- 관측 처리, 보정, HMM은 교체할 수 있는 인터페이스로 분리한다. 모델과 설정의 묶음을 보존한다.
- 새 기본값은 새 요청과 새 점유 세션부터 적용한다.
- 아래 값은 생성 당시 값을 유지한다.
  - 기존 승인의 만료와 횟수
  - 진행 중인 점유 세션의 종료 정책과 대여시간 기준 시각
- 기존 승인과 진행 중인 점유 세션에도 현재 신뢰, 온라인, 안전 상태 검사를 계속 적용한다.
- 접근 정책 버전이 바뀌면 재승인을 요구하는 규칙도 유지한다.
- 모델과 결합된 임계값은 모델과 함께 검증셋으로 검증한다.
- 근접 추정은 장소마다 버전이 붙은 모델 파일을 시작할 때 읽는다 (#40).
- 모델 파일은 앵커별 경로손실 값 `A`, `n`, `σ`, 기기 배치, HMM 전이와 보정 값을 묶는다.
- 모델 파일은 장소 ID와 기기 ID로 앵커와 기기 배치를 식별한다.
- 운영 임계값은 `Settings`에 둔다. 모델 파일에는 검증에 쓴 임계값을 기록한다.
- 파일 내용을 바꾸면 새 버전을 만든다. 같은 버전의 파일을 덮어쓰지 않는다.
- 판정 기록이 참조하는 과거 버전 파일은 판정 재현에 쓸 수 있도록 보존한다.
- §4의 성능 목표와 표본 수는 평가 기준이다. 평가 기준은 운영 설정과 따로 버전을 관리한다.
- 팀은 합의해서 평가 기준을 고칠 수 있다. 한 평가 회차 안에서는 평가 기준을 고정한다. 평가 기준을 바꾸면 변경 전 결과와 변경 후 결과를 구분한다.
- 아래 규칙은 수치를 조정해서 완화하지 않는다.
  - 서버 인가
  - 소유권 검사
  - 중복 실행 금지
  - 안전 확인 후 해제
- API, 상태, 식별자, DB 관계를 바꾸려면 호환성과 데이터 이전을 먼저 검토한다.

|---|---|

데이터 관계는 `architecture.md` §6에 정의한다. 테이블 수는 고정하지 않는다.

### 1.4 데이터 공개와 폐기

- 평가가 끝나면 관측 기록과 로그에서 계정 ID를 지운다. 계정 ID를 지운 데이터는 공개용 데이터셋으로 보존한다.
- 프로젝트가 끝나면 토큰 해시와 비콘 식별자를 폐기한다.
- 수집 회차에 연결된 관측은 운영 관측의 보존기간과 별도로 보존한다.

## 2. 기능 요구사항

### FR-01 계정·비콘 1회 연결

- 범위: 서버
- 요구:
  - 서버는 계정과 폰의 iBeacon 식별자를 한 번 등록한다. 서버는 등록한 계정에 토큰을 발급한다.
  - 토큰은 서버가 만든 32바이트 무작위 값이다. 서버는 토큰의 해시만 저장한다 (NFR-08).
  - 방문자는 장소마다 등록하지 않는다.
  - 서버는 다른 계정에 이미 등록된 비콘 식별자를 거부한다.
  - 계정당 활성 비콘은 하나 이하다.
  - 활성 비콘을 등록하면 서버는 같은 계정의 다른 비콘을 비활성화한다.
  - 서버는 비콘 중복 검사, 기존 비콘 비활성화, 등록과 감사 기록을 한 트랜잭션에서 반영한다.
  - 등록을 거부하거나 저장에 실패하면 서버는 기존 활성 비콘을 유지한다.
  - 비활성 비콘 등록은 같은 계정의 다른 비콘을 비활성화하지 않는다.
- 인수 기준: 지표 5
- 관련: FR-08, NFR-08

### FR-02 비콘 백그라운드 송출

- 범위: 범위 밖 (앱)
- 요구:
  - 앱은 등록한 식별자로 iBeacon을 계속 송출한다.
  - 앱은 비콘 송출 상태를 표시한다. 앱은 송출 중단을 감지한다.

### FR-03 소유자 승인

- 범위: 서버 (UI는 앱)
- 요구:
  - 서버는 제한 기기의 승인 요청 목록을 제공한다.
  - 권한이 있는 소유자가 승인하거나 거부하면 서버는 결과를 즉시 반영한다.
  - 대기 승인이 생기면 서버는 소유자 앱에 알린다. 알림이 전달되지 않아도 서버는 대기 승인을 대기 목록에 남긴다.
  - 소유자는 승인 요청 알림을 눌러서 Android 앱의 승인 요청 화면을 연다. 소유자는 승인 요청 화면에서 승인하거나 거부한다.
  - 알림은 소유자를 웹 화면이나 AI 호스트 화면으로 보내지 않는다.
  - 앱은 소유자의 결정만 서버에 전달한다. 서버는 승인 권한, 대기 상태, 정책 버전을 검증하고 결과를 기록한다.
  - 승인이 대기 상태이고 정책 버전이 같을 때만 서버는 소유자의 결정을 반영한다.
  - 결정을 반영하지 못하면 서버는 이유를 구분한다. 이유는 이미 결정한 승인, 정책 버전 불일치, 대기 만료다.
  - 같은 승인 ID에 같은 결정자가 같은 결정을 재전송하면 서버는 기존 결과를 성공으로 반환한다.
  - 재호출 시각은 같은 결정의 비교에 넣지 않는다. 서버는 결정과 유효시간과 감사 기록을 다시 쓰지 않는다.
  - 반대 결정이나 다른 결정자의 재호출은 충돌이다. 서버는 기존 결정을 보존한다.
  - 재호출에서도 CORE는 승인 권한을 검사한다. 기존 승인 결과의 반환은 실행 허가가 아니다.
  - 같은 요청자, 기기, 동작, 정책 버전에 만료되지 않은 대기 승인이 있으면 서버는 새 승인을 만들지 않는다. 서버는 기존 대기 승인을 반환한다.
  - 서버는 승인 결과를 기존 MCP 도구 계약으로만 다룬다.
  - 방문자가 다시 요청하면 AI 호스트가 `request_use`를 호출한다. 서버는 ⓪~⑥을 처음부터 다시 적용한다. 서버는 ④에서 유효한 승인을 확인한다.
  - 승인이 아직 대기 중이거나 재승인이 필요하면 서버는 `NEED_APPROVAL`을 반환한다. 사유는 대기, 거부, 대기 만료, 승인 만료를 구분한다.
  - 미결: 독립 AP에서 소유자 앱에 알리는 수단. 후보에는 앱 연결 유지, 주기 조회, FCM이 있다. FCM은 인터넷 연결이 필요해서 채택하지 않았다.
  - 미결: 소유자 단말이 AP 밖에 있을 때의 동작
  - 대기 승인은 신청 시점부터 10분이 지나면 만료한다. 10분은 초기 기준이다 (§1.2).
  - 같은 대기 신청을 다시 호출하면 서버는 기존 신청을 반환한다. 서버는 만료 시각을 연장하지 않는다.
  - 만료한 대기 신청은 새 신청을 막지 않는다. 서버는 만료 뒤의 새 신청을 받는다.
  - 서버는 만료한 신청에 대한 승인 결정을 반영하지 않는다.
  - 서버는 대기 만료와 소유자의 명시적 거부를 구분한다. 대기 만료의 사유 코드는 `APPROVAL_REQUEST_EXPIRED`다.
  - 미결: 방문자에게 결과를 알릴지 여부
- 인수 기준: 지표 5
- 관련: FR-14

### FR-04 기능 발표(발견)

- 범위: 연동
- 요구:
  - 기기는 부팅하면 기능과 점유 방식을 MQTT `announce` 토픽에 retained 메시지로 발표한다.
  - 서버는 발표를 받아서 기기를 발견한다.
  - 서버는 처음 보는 기기를 `discovered`로 저장한다. 발표는 신뢰 부여가 아니다.
  - 내용이 같은 재발표는 신뢰 상태를 바꾸지 않는다.
  - 신뢰한 기기가 다른 기능이나 다른 점유 방식으로 발표하면 서버는 신뢰 상태를 `discovered`로 되돌린다. 서버는 새 값을 저장하고 변경을 감사 로그에 기록한다.
  - 서버는 현재 기기 연결 ID와 그 연결의 첫 수신 시각을 저장한다.
  - 진행 중인 점유가 있는 기기의 발표 내용이 바뀔 때 기기를 격리할지는 상태 관리가 정한다.
- 인수 기준: 지표 5
- 관련: FR-13

### FR-05 RSSI 보고

- 범위: 연동
- 요구:
  - 기기는 약 1초 간격으로 비콘 식별자와 RSSI를 `rssi` 토픽에 보고한다.
  - 서버는 보고를 수신한다.
  - 서버는 등록된 활성 비콘의 관측만 저장한다.
  - 서버는 관측에 서버 수신 시각, 기기 연결 ID, 순번을 함께 저장한다.
  - 서버는 기기, 기기 연결 ID, 순번, 비콘이 같은 관측을 한 번만 저장한다.
  - 수집 관측도 같은 IOT 검증과 DB 저장 경로를 쓴다. IOT는 수집 여부와 라벨을 받지 않는다.
  - 수집 라벨은 RSSI 라벨 수집 도구만 쓴다. 운영 경로의 관측에는 수집 라벨이 없다.
- 인수 기준: 지표 8

### FR-06 서버 허가 후 실행

- 범위: 연동
- 요구:
  - 기기는 서버의 `OK!(command_id)`를 받았을 때만 구동한다.
  - 서버는 허가한 명령만 `cmd` 토픽으로 보낸다.
  - 서버는 물리 명령마다 고유한 `command_id`를 발급한다.
  - 서버와 기기는 `command_id`로 명령과 결과를 연결하고 중복 실행을 막는다.
  - 외부 요청의 중복 방지 보장기간(FR-22)은 `command_id` 기록에 적용하지 않는다. 서버가 외부 `request_id`를 비워도 기기는 `command_id` 기록을 지우지 않는다.
  - 다른 구동 명령이 진행 중이면 기기는 새 명령을 대기열에 넣지 않는다. 기기는 구동 전에 `DEVICE_BUSY`로 거부한다.
  - 서버는 거부된 명령을 새 명령 ID로 자동 재시도하지 않는다.
- 인수 기준: 지표 3, 5
- 관련: FR-18, FR-19

### FR-07 실행·안전 상태 보고

- 범위: 연동
- 요구:
  - 기기는 실행 결과를 `result` 토픽에, 물리 관측을 `status` 토픽에 보고한다.
  - 기기는 반납 검사 요청을 `safety_check` 토픽으로 받는다. 기기는 반납 검사 결과를 `safety_check_result` 토픽에 보고한다.
  - 실행 결과가 불명이거나 안전을 확인하지 못하면 서버는 기기를 `FAULT`로 격리한다.
  - 서버는 실행 결과를 확인한다. 서버는 시간 초과나 연결 끊김을 실행 성공으로 보지 않는다.
  - 기기가 실행 실패를 보고하면 서버는 기기를 `FAULT`로 격리한다. 검증한 `DEVICE_BUSY` 거부는 예외다. 서버는 승인 사용분을 보류하고 불명확한 점유 세션을 보존한다.
  - 전송 확인과 명령 접수는 실행 성공이 아니다. 서버는 명령별 완료 근거를 확인한다.
  - 결과 대기가 끝나도 서버는 늦은 결과를 수신한다. 같은 결과 사건은 한 번만 정산한다.
  - 늦은 성공만으로 서버는 `FAULT`를 해제하거나 종료한 점유 세션을 되살리지 않는다.
  - 기기가 접수와 구동 전에 `DEVICE_BUSY`로 거부한 결과는 실행 실패가 아니다. 서버는 검증한 `DEVICE_BUSY` 거부만으로 기기를 `FAULT`로 격리하지 않는다.
  - 서버는 `DEVICE_BUSY` 거부를 확실한 미전송으로 바꾸지 않는다. 사용분과 예약의 정리는 FR-19를 따른다.
  - 기기가 접수했거나 구동했다는 근거가 있거나 결과가 상충하면 서버는 이 예외를 적용하지 않는다.
  - 서버는 서버의 타임아웃과 통신 오류를 기기가 보고한 불명과 구분한다.
  - 종료 안전은 실행 성공과 따로 확인한다. 서버는 종료 안전을 이번 반납의 반납 검사 결과로 확인한다.
  - 기기는 반납 검사 요청을 받은 뒤 물리 조건을 새로 검사한다. 검사 결과는 `passed`, `not_ready`, `fault`, `unknown` 중 하나다.
  - 일반 `status` 보고와 명령 실행 성공은 반납 검사를 대신하지 못한다.
  - 기기가 검사 기준을 모르거나 결과를 확인하지 못하면 서버는 통과로 보지 않는다.
  - 안전 보고 허용 나이의 초기 기준은 3초다 (§1.2).
  - 서버와 시뮬레이터는 `architecture.md` §5의 MQTT 계약 v1을 개발 기준으로 쓴다.
  - 실행 응답 제한의 초기 기준은 전송 시도 뒤 3초다 (§1.2).
  - 서버와 기기는 폐쇄망 안의 시각원으로 동기화한다. 기기별 최대 시각 오차는 실측한 뒤 설정한다 (#140 A안).
  - 시각 신뢰를 검증하기 전 서버는 실행 허가와 안전 확인을 차단한다. 펌웨어는 새 명령을 `CLOCK_UNVERIFIED`로 거부한다.
  - 미결 — #140: 실제 기기의 동기화 방식, 재동기화 간격과 최대 시각 오차다. 실측 전 임의의 수치를 쓰지 않는다.
  - 미결: 실제 기기의 안전 센서 조합, 반납 검사의 근거 제공 능력과 동작별 완료 근거다. 팀이 펌웨어 담당을 배정한 뒤 검증한다.
  - 미결: IR 무드등의 `light_on` 보고 근거. IR 무드등은 켜짐을 관측할 수단이 없다. 조도 센서 추가 같은 근거를 정해야 한다 (#61).
  - 미결: 스피커의 재생 관측 필드와 `on`·`off`의 완료 근거 (#61).
- 인수 기준: 지표 6
- 관련: NFR-04

### FR-08 통합 MCP 엔드포인트

- 범위: 서버
- 요구:
  - 서버는 `/mcp`에서 MCP Streamable HTTP를 직접 제공한다.

  - 서버는 토큰을 검증한다. 서버는 토큰이 없거나 무효한 호출을 거부한다.
  - 서버는 받은 토큰의 SHA-256 해시를 계산한다. 서버는 저장한 토큰 해시와 대조해서 계정을 찾는다.
- 인수 기준: 지표 7

### FR-09 MCP 도구 6개

- 범위: 서버
- 요구:
  - 서버는 아래 도구 6개를 제공한다.
  - `target_spec`은 아래 세 방식을 지원한다.
    - 근접 지정: `nearest:locker`
    - 명시적 지정: `locker-1`
    - 허용 후보 중 배정: `any:locker`
  - 동작은 `open`, `on`, `off`를 지원한다.
  - 스피커의 `on`은 재생이고 `off`는 정지다. 스피커에 새 동작을 추가하지 않는다.
  - AI 호스트는 재질문 뒤의 요청과 승인 뒤의 사용 재요청에 새 `request_id`를 쓴다. 서버는 새 요청을 원래 요청이나 승인과 연결한다.
  - AI 호스트는 같은 요청을 다시 전송할 때 기존 `request_id`를 유지한다.
  - 응답에는 판정, 사유, 기기 정보, 본인의 요청 핸들과 `use_id`를 담는다.
- 인수 기준: 지표 7
- 관련: FR-10, FR-11, FR-21

|---|---|
| `find_available_devices` | 근접, 신뢰, 온라인, 사용 가능, 미점유 조건을 만족한 후보를 반환한다. 후보는 '조작 가능'과 '승인 필요'로 나눈다. 비공개 기기와 점유 주체는 보여 주지 않는다. 비콘을 수신하지 못했으면 빈 목록을 반환한다. |
| `get_device_state` | 근접 검사 없이 기기 상태를 조회한다. 공개 기기는 유효한 토큰으로 조회한다. 비공개 기기는 소유자이거나 현재 본인의 점유 세션이 있어야 조회한다. 점유 주체는 보여 주지 않는다. |
| `request_access` | 제한 기기의 접근 승인을 요청한다. 승인 요청은 실행 허가가 아니다. |
| `request_use` | `target_spec`, 동작, `request_id`로 사용을 요청한다. 서버는 중복, 근접, 정책, 점유를 검사한 뒤 실행한다. |
| `release_use` | 본인 `use_id`의 사용 종료를 요청한다. 서버는 유효한 사용 권한, 기기의 해제 정책, 안전 상태를 확인한다. |
| `get_use_status` | 근접 검사 없이 본인의 점유 세션과 종료 이력을 조회한다. 사용 권한이 만료돼도 이력 보존기간 안에서는 조회할 수 있다. 서버는 타인의 핸들을 거부한다. |

### FR-13 기기 신뢰·온라인 판정

  - 오래된 관측과 과거 명령 결과는 현재 온라인·안전 시각을 갱신하지 않는다.
  - 온라인 유지 시간의 초기 기준은 유효한 기기 메시지의 마지막 수신부터 15초다 (§1.2).

### FR-14 기기별 접근 정책·승인

- 범위: 서버
- 요구:
  - 서버는 기기별 접근 정책 설정 기능과 접근 요청 기능을 제공한다.
  - 서버는 사용 요청을 받으면 승인 여부를 검사한다.
  - 접근 정책은 `open` 또는 `restricted`다. `open`은 개방이고, `restricted`는 승인이 필요하다.
  - 승인은 **요청자, 기기, 동작, 정책 버전**에 묶인다.
  - 승인 권한이 있는 계정만 승인하거나 거부한다.
  - 사물함의 기본 승인 방식은 `one_time`이다. 서버는 사물함을 실행한 뒤 승인을 소진한다.
  - 조명의 기본 승인 방식은 `time_window`다. 방문자는 유효기간 안에서 조명을 반복해서 쓸 수 있다.
  - 미결: 스피커의 기본 승인 방식 (#61).
  - 승인 횟수와 유효시간은 기기마다 설정한다.
  - 서버는 승인 시각에 승인 유효시간을 더해서 승인의 만료 시각을 정한다. 승인 유효시간은 승인을 만든 당시 정책 버전의 값이다.
  - 기간형 승인의 횟수가 무제한이어도 서버는 요청별 승인 사용분을 기록한다. 서버는 횟수 검사만 생략한다.
  - 아래 경우에는 재승인이 필요하다.
    - 소유자가 승인을 거부했다.
    - 승인이 만료됐다.
    - 정책이 바뀌었다.
  - 서버는 사용 횟수를 넘은 요청과 승인과 다른 동작의 요청을 거부한다.
  - 정책 변경은 진행 중인 점유에 소급하지 않는다.
  - 공개 범위(`public` 또는 `private`)는 승인 필요 여부와 따로 관리한다.
  - 서버는 비공개 기기를 주변 목록에서 숨긴다. 비공개 기기의 과거 사용 이력은 점유 세션 기록 조회로만 볼 수 있다.
  - 서버는 접근 정책의 버전별 내용을 보존한다. 접근 정책 버전은 운영 설정 버전과 따로 관리한다.
  - 소유자가 정책을 바꾸면 서버는 새 정책 버전을 추가한다. 서버는 과거 정책 버전의 내용을 바꾸지 않는다.
  - 운영 수치만 바뀌었으면 서버는 기존 승인을 무효화하지 않는다.
  - 승인 기본 유효시간의 초기 기준은 승인 시점부터 1시간이다 (§1.2).
  - 서버는 승인 시각에 생성 당시 정책 리비전의 `approval_ttl_sec`를 더해서 승인 만료 시각을 계산한다.
  - 1시간은 접근 승인에만 적용한다. 복구의 소유자 승인(NFR-04)과 종료 안전·기기 보고 시간에는 적용하지 않는다.
  - 승인 전 대기 신청의 만료는 FR-03을 따른다. 대기 만료는 승인 만료와 다른 시간이다.
- 인수 기준: 지표 5
- 관련: FR-03, FR-12A, FR-19

### FR-15 계정–비콘 대조

### FR-16 근접 추정·대상 선택

- 범위: 서버
- 요구:
  - 서버는 앵커별 RSSI에 관측 모델과 HMM을 적용한다. 서버는 후보 중 사후확률이 가장 큰 기기를 선택한다 (③).
  - 판정은 ①에서 조회한 활성 비콘 하나를 근접 추정에 넘긴다. 여러 비콘의 확률을 합치지 않는다.
  - 서버는 장소의 전체 상태로 사후확률을 계산한다. 전체 상태는 아래 두 가지다.
    - 장소의 `trusted` 기기마다 그 기기 앞 상태
    - "어느 기기 앞도 아님" 상태
  - `FAULT` 기기, 오프라인 기기, 요청 종류가 다른 기기도 `trusted`이면 전체 상태에 넣는다. 방문자는 후보가 아닌 기기 앞에도 설 수 있다.
  - 서버는 후보의 사후확률을 후보끼리 다시 정규화하지 않는다. 후보 사후확률의 합은 1 이하다.
  - 서버는 후보 밖 상태의 확률을 어느 후보에도 더하지 않는다.
  - 서버는 `trusted`가 아닌 기기가 보낸 RSSI를 근접 추정에 쓰지 않는다.
  - 근접 추정은 파라미터와 기기 배치를 모델 파일에서 읽는다. DB의 `node`에는 근접 파라미터를 두지 않는다.
  - `tools/data_collection`은 비콘, 라벨, 시작 시각과 끝 시각을 담은 수집 회차를 DB에 기록한다. 기록 접점은 `AdminRepository`다 (#131).
  - 수집 라벨은 기기 1~7 앞 또는 `none`이다. "앞"의 거리 기준은 근접 추정 구현 담당이 spec에서 정한다.
  - DB는 비콘과 관측 시각으로 회차를 찾아 관측에 수집 회차 ID를 저장한다.
  - 같은 비콘의 수집 회차 구간이 겹치면 DB는 새 회차를 거부한다.
  - 평가 스크립트는 `tools/evaluation`이 맡는다. 같은 회차의 프레임은 서로 다른 데이터 분할에 섞지 않는다.
  - 미결: 관측 특징, 결측값 처리 방법, HMM 상태와 전이, 보정 방법
  - 미결: 무드등 장소의 수집 라벨. 무드등 장소에는 기기가 하나다 (#61).
- 인수 기준: 지표 1, 8
- 관련: FR-17, NFR-02, NFR-06

### FR-17 비용 기반 재질문

- 범위: 서버
- 요구:
  - 사후확률이 설정 임계값 미만이면 서버는 기기를 실행하지 않고 `ASK`를 반환한다. 임계값의 초기값은 사물함 0.95, 조명 0.75다.
  - 서버는 임계값과 비교하는 사후확률을 다시 정규화하지 않는다 (FR-16).
  - 서버는 요청 종류에 따라 적용할 임계값을 고른다. 요청 종류는 명시적 지정 요청과 그 외 요청이다.
    - 그 외 요청에는 위 초기값의 임계값을 적용한다.
    - 명시적 지정 요청에는 별도 임계값을 적용한다. 별도 임계값은 그 외 요청의 임계값보다 낮다. 서버는 별도 임계값을 설정에서 받는다.
  - 명시적 지정 요청도 사후확률이 명시적 지정 요청의 임계값 미만이면 서버는 기기를 실행하지 않는다. 서버는 이동을 안내한다.
  - 근접 임계값은 검증셋에서만 조정한다. 시험셋으로 평가하기 전에 임계값을 고정한다.
  - 미결: 명시 지정 임계값의 수치. 근접 추정 담당이 검증셋으로 실험한 뒤 정한다. 설정 이름은 `threshold_explicit_locker`, `threshold_explicit_light`, `threshold_explicit_speaker`다. 기본값 `None`이면 명시 지정 실행을 허가하지 않는다.
  - 미결: 스피커의 근접 임계값. 설정 이름은 `threshold_speaker`다. 기본값 `None`이면 스피커 실행을 허가하지 않는다 (#61).
  - 미결: 오류 비용
- 인수 기준: 지표 2
- 관련: FR-16

### FR-18 결정론적 판정 순서

- 범위: 서버
- 요구:
  - 서버는 인증과 입력 검증을 마친 뒤 아래 순서를 적용한다.
  - **기본값은 거부**다.
  - 판정 중 예상하지 못한 예외가 나면 서버는 `DENY`와 `INTERNAL_ERROR`로 거부한다. 서버는 이 사유를 정상 거부에 쓰지 않는다.
  - `INTERNAL_ERROR`로 거부한 요청을 같은 `request_id`와 같은 입력으로 재전송하면 서버는 다시 판정한다 (#76).
  - 서버는 호스트 응답에 일반 안내만 넣고 예외 내용은 넣지 않는다. 상세는 감사 기록에만 남긴다 (NFR-08).
  - 공용형의 점유 검사 생략을 빼면, 호스트나 방문자의 발화로 단계를 생략할 수 없다.
  - 판정은 아래 다섯 가지다.
    - `OK`: 허가
    - `BUSY`: 기기 점유 충돌, 사용자 점유 충돌 또는 다른 구동 명령 진행 중
    - `ASK`: 재질문
    - `DENY`: 거부
    - `NEED_APPROVAL`: 승인 필요
  - 서버는 허가하지 않은 요청으로 기기를 실행하지 않는다. 서버는 허가하지 않은 요청의 새 점유를 유지하지 않는다.
  - 서버는 **실행 직전에 허가, 근접, 대상을 재검사**한다. 재검사는 자기 요청의 예약을 타인 점유로 보지 않는다.
  - 공용형 기기 요청은 ⑤⑥과 점유 세션 생성을 건너뛴다. 서버는 공용형 기기 요청에도 승인 사용분을 원자적으로 확보한다.
  - 판정은 대여형과 공용형에 같은 예약 접점을 호출한다. DB가 점유 방식을 보고 ⑤⑥과 점유 세션 생성을 건너뛴다 (FR-19).
  - 서버는 판정 한 건마다 판정 기록을 한 번 저장한다. 서버는 `ASK`, `BUSY`, `DENY`도 저장한다 (FR-22).
  - 판정은 최초 허가와 필요한 예약 뒤 실행 인계 정보를 상태 관리에 전달한다.
  - 판정은 실행 직전 재검사를 제공한다. 상태 관리는 전송 직전에 재검사를 호출한다.
  - 재검사 거부와 검사 오류는 구분한다. 두 경우 모두 상태 관리는 전송을 차단한다.
  - 같은 내부 요청을 다시 인계해도 서버는 기존 진행 상태나 결과를 반환한다. 새 명령을 만들지 않는다.
  - 실행 인계는 최초 대여, 기존 대여의 재조작, 공용형 조작을 구분한다.
  - 대여 중인 본인의 새 조작은 새 요청과 새 명령이다. 서버는 새 요청과 새 명령을 기존 `use_id`에 연결한다.
  - 판정은 재조작에도 본인 점유, 현재 접근 정책, 근접 조건을 검사한다.
  - 서버는 실행 성공과 필요한 저장 반영을 확인하기 전에 호스트에 완료를 안내하지 않는다.
  - 대표 흐름은 아래와 같다.
    1. AI 호스트가 `request_use(nearest:locker, open, request_id)`를 호출한다.
    2. 서버가 계정을 식별하고 내부 요청 ID를 연결한다.
    3. 서버가 ⓪~⑥을 검사하고 승인 사용분을 확보한다.
    4. 점유 세션이 `RESERVED`가 된다. 서버가 `use_id`를 만든다.
    5. 서버가 실행 직전 재검사를 한다.
    6. 서버가 기기에 `OK!(command_id)`를 보낸다.
    7. 서버가 실행을 확인하고 승인을 소진한다.
    8. 서버가 상태를 `ACTIVE`로 바꾼다.
    9. 서버가 호스트에 완료와 `use_id`를 안내한다.
- 인수 기준: 지표 3, 4, 5
- 관련: FR-15, FR-16, FR-17, FR-19, FR-22

| 순서 | 검사와 결과 |
|---|---|
| ⓪ 중복 | 서버는 `(계정, request_id)`와 정규화한 입력을 대조한다. 같으면 기존 결과와 진행 상태를 반환한다. 같은 키에 다른 입력이 오면 충돌로 거부한다. 다른 계정의 결과는 반환하지 않는다. 정규화한 입력은 대상 지정, 동작, 원 요청 연결 ID로 구성한다. 외부 요청 ID, 수신 시각, 호스트 종류는 넣지 않는다. |
| ① 비콘 | 서버는 장소의 앵커가 토큰 계정의 등록 비콘을 최근 T초 안에 수신했는지 검사한다. 원격 요청이거나 관측이 없으면 `DENY`다. |
| ② 후보 | 서버는 신뢰, 온라인, 요청 종류가 맞고 `FAULT`가 아니며 재시작 복원을 마친 기기로 후보를 구성한다 (#82). 정책이나 점유 때문에 다른 물리 대상을 고르지 않도록, 정책과 점유는 대상을 확정한 뒤 ④~⑥에서 검사한다. |
| ③ 근접 | 서버는 앵커별 RSSI에 관측 모델과 HMM을 적용해서 장소의 전체 상태로 사후확률을 계산한다. 서버는 후보의 사후확률을 다시 정규화하지 않고, 후보 중 사후확률이 가장 큰 기기를 선택한다. 사후확률이 설정 임계값 미만이면 실행하지 않고 `ASK`다. 임계값의 초기값은 사물함 0.95, 조명 0.75다. 스피커의 임계값은 미결이다. 명시적 지정 요청에는 별도 임계값을 적용한다 (FR-17). |
| ④ 정책 | 서버는 기기의 정책과 접근 승인을 검증한다. 승인이 필요하면 `NEED_APPROVAL`이다. 정책이 허용하지 않으면 `DENY`다. |
| ⑤ 기기 점유 | 타인이 점유했거나 본인 세션이 `ACTIVE`가 아니면 기기 사유의 `BUSY`다. 본인 `ACTIVE` 세션이면 기존 점유에 재조작을 연결한다. |
| ⑥ 사용자 점유 | 계정이 같은 `exclusive_group`에서 이미 다른 기기를 점유하고 있으면 사용자 사유의 `BUSY`다. 서버는 ⑤⑥ 검사와 예약 생성을 한 트랜잭션으로 묶는다. |

### FR-19 원자적 점유·상태 머신

- 범위: 서버
- 요구:
  - **원자성과 멱등성**
    - 서버는 SQLite 단일 쓰기 경로와 `BEGIN IMMEDIATE`로 기기 점유 확인, 사용자 점유 확인, `RESERVED` 생성을 하나로 묶는다.
    - 동시 요청과 재전송이 있어도 서버는 이중 점유와 중복 물리 실행을 막는다.
    - 서버 기록과 기기의 중복 실행 방지 계약을 함께 정의한다.
    - 외부 `(계정, request_id)`의 중복 방지는 FR-22의 보장기간 안에서 보장한다. 진행 중이거나 미해결인 요청은 기간과 관계없이 보장한다.
  - **승인 사용분**
    - 서버는 실행 전에 요청별 승인 사용분을 원자적으로 예약한다. 예약한 사용분은 남은 횟수에서 뺀다.
    - 대여형 요청은 승인 사용분 예약과 점유 예약을 같은 트랜잭션에서 한다.
    - 공용형 제한 기기의 요청도 같은 쓰기 경로의 `BEGIN IMMEDIATE` 트랜잭션 하나에서 승인 사용분을 예약한다.
    - 공용형 요청에서 서버는 기기 점유 확인, 사용자 점유 확인, 점유 세션 생성을 건너뛴다. 서버는 기기 상태를 바꾸지 않는다.
    - 공용형 기기의 접근 정책이 `open`이고 요청에 승인이 없으면 서버는 아무것도 저장하지 않고 예약 성공을 반환한다.
    - 실행 성공을 확인하면 서버는 소진을 확정한다.
    - 명령을 보내지 않은 것이 확실할 때만 서버는 승인 사용분을 자동으로 반환한다. 재검사 실패가 한 예다.
    - 명령을 보낸 뒤 결과가 실패하거나 불명이면 서버는 승인 사용분과 불명확한 점유를 보류한다. 서버는 복구한 뒤 실행 여부에 따라 정산한다.
    - 예외는 기기가 검증된 `DEVICE_BUSY`로 접수·실행 전에 거부한 명령 하나뿐이다. 서버는 이번 요청의 승인 사용분을 반환한다.
    - 서버는 실행 여부를 확인하지 못한 명령을 미실행으로 보지 않는다. 서버는 그 명령의 승인 사용분을 자동으로 반환하지 않는다.
  - **장애와 재전송**
    - 서버와 기기는 명령 기록과 처리 기록을 재시작 뒤에도 보존한다.
    - 서버와 기기는 같은 `command_id`를 다시 실행하지 않는다.
    - 전송을 시도한 뒤 응답 유실이나 재시작으로 실행 여부가 불명확하면 서버는 새 명령으로 재시도하지 않는다. 서버는 `FAULT` 복구로 넘긴다.
    - 기록만으로 실행 여부를 확정하지 못하면 서버는 물리 상태를 확인할 때까지 새 허가를 막는다.
  - **재시작 복원**
    - 서버는 재시작하면 끝나지 않은 요청, 명령, 점유 세션, 승인 사용분, 복구 건을 기기별로 함께 조회한다.
    - 조회 대상에는 미해결 `FAULT` 기기와 점유 세션이 없는 공용형 명령의 승인 사용분도 넣는다.
    - 서버는 복원 조회의 실패를 빈 목록으로 바꾸지 않는다.
    - 서버는 저장한 시각을 그대로 복원한다. 서버는 저장한 시각을 재시작 시각으로 덮어쓰지 않는다.
    - 과거의 안전 근거는 복원 자료다. 서버는 현재 실행 상태와 안전 상태를 다시 확인한다.
    - 서버는 기기의 복원과 확인을 끝내기 전에 그 기기의 새 실행과 재사용을 허가하지 않는다.
    - 공용형 기기의 과거 참여자 목록은 복원 조회의 대상이 아니다. 이 규칙은 대여형 점유 세션의 복원을 생략하지 않는다.
  - **예약 이후 저장**
    - 서버는 전송 시작, 미전송 취소, 실행 결과, 접수·실행 전 거부, 종료, 복구를 사건별로 원자적으로 반영한다.
    - 취소와 전송 시작이 경합하면 한쪽만 성공한다. 취소한 예약은 전송을 시작할 수 없다.
    - 같은 사건의 재호출은 기존 결과를 반환한다. 내용이 다르면 서버는 기록을 덮어쓰지 않고 충돌을 반환한다.
    - 서버는 저장 충돌과 저장 오류를 구분한다. 반영 여부가 불명이면 식별자로 결과를 다시 조회한다.
    - 전송 시작 기록만으로 서버는 실제 전송, 실행 성공, 확실한 미전송을 판단하지 않는다.
  - **구동 중 추가 명령 제한**
    - 같은 기기에 결과를 확정하지 못한 구동 명령이 있으면 서버는 다른 새 구동 명령의 전송을 시작하지 않는다. 본인 재조작과 공용형 조작에 모두 적용한다.
    - 서버는 전송을 시작할 때 같은 기기의 다른 미완료 구동 명령, 기기 상태, 점유 세션 상태를 원자적으로 검사한다.
    - 서버는 같은 명령의 중복 시작과 다른 명령끼리의 경합을 구분한다.
    - 기기 상태 `ACTIVE`는 대여 중이라는 뜻이다. 구동부가 동작 중이라는 `busy` 보고와 구분한다.
    - 기기가 검증된 `DEVICE_BUSY`로 거부하면 서버는 접수·실행 전 거부로 저장한다. 접수·실행 전 거부는 서버의 확실한 미전송과 다른 결과다.
    - 서버는 접수·실행 전 거부를 저장할 때 명령 기록과 근거, 이번 요청의 승인 사용분 반환, 감사 기록을 한 트랜잭션에서 반영한다.
    - 최초 대여의 거부이면 서버는 이번 예약의 취소도 같은 트랜잭션에서 반영한다.
    - 실행 중 거부의 공동 사유는 `COMMAND_IN_PROGRESS`다. CORE는 `BUSY`로 반환한다 (FR-19).
    - 접수·실행 전 거부만으로 서버는 기기를 `FAULT`로 두지 않는다.
    - 명령을 접수했거나 구동했다는 근거가 있으면 서버는 이 예외를 적용하지 않는다. 결과가 상충할 때도 같다. 서버는 불명·충돌·격리 규칙을 따른다.
    - 서버는 결과 대기 시간 초과를 `DEVICE_BUSY`로 추정하지 않는다.
    - 같은 거부 결과를 다시 받아도 서버는 승인 사용분을 한 번만 반환한다.
  - **본인 재조작**
    - 서버는 재조작 요청과 기존 점유 세션의 계정, 기기, 세션 연결을 저장 기록으로 검사한다. 서버는 인계 값만으로 기존 점유를 바꾸지 않는다.
    - 재조작의 확실한 미전송 취소는 이번 요청의 명령과 승인 사용분만 정리한다.
    - 재조작의 취소와 접수·실행 전 거부는 기존 점유, `rental_due_at`, 기존 대여의 승인 사용분을 바꾸지 않는다.
    - 재조작이 성공해도 서버는 `rental_due_at`을 갱신하지 않는다. 서버는 이번 요청의 승인 사용분을 정산한다.
    - 재조작이 실패하거나 결과가 불명이면 서버는 격리 규칙을 따른다. 서버는 기존 점유를 자동으로 종료하지 않는다.
    - 기기가 `CLOSING` 또는 `FAULT`이면 서버는 새 조작을 시작하지 않는다.
    - 반납을 시작해서 `CLOSING`이 되면 서버는 새 명령의 전송 시작을 막는다.
    - 서버는 전송 시작과 반납 시작에서 기기와 점유 세션의 현재 상태를 원자적으로 검사한다.
  - **대여형**
    - 기기 상태는 `AVAILABLE → RESERVED → ACTIVE → CLOSING → AVAILABLE` 순서로 바뀐다.
    - 최초 대여의 예약을 확실한 미전송으로 취소하면 서버는 기기를 `RESERVED`에서 `AVAILABLE`로 되돌린다. 서버는 점유 세션을 `cancelled` 사유로 `CLOSED`에 둔다.
    - 이상을 감지하면 어느 상태에서든 기기는 `FAULT`가 된다 (NFR-04).
    - 점유 예약이 성공하면 서버는 계정과 기기에 묶인 `use_id`를 만든다.
    - 실행을 확인하면 서버는 상태를 `ACTIVE`로 바꾼다. 서버는 대여시간 기준 `rental_due_at`을 보존한다.
    - 서버는 실행 성공과 필요한 저장 반영을 확인한 뒤에만 `use_id`를 호스트에 반환한다.
    - 점유 세션 상태는 `RESERVED → ACTIVE → CLOSING → CLOSED` 순서로 바뀐다.
    - 서버는 종료 시각 `closed_at`과 생성 당시 종료 정책을 보존한다.
    - 서버는 초과시간을 별도 값으로 저장하지 않고 대여시간 기준 시각으로 계산한다.
    - 종료 전에는 현재 시각을 쓴다. 종료 뒤에는 `closed_at`을 쓴다. 초과 전의 초과시간은 0이다.
    - `rental_due_at`은 접근 승인 만료가 아니다. 기존 `expires_at`의 대여 의미는 `rental_due_at`으로 분리한다.
    - 종료 사유 값은 `release`, `leave`, `timeout`, `fault`, `cancelled`다. 대여형은 이탈과 대여시간 초과로 종료하지 않는다.
  - **예약 대기 제한**
    - 예약 대기 제한의 초기 기준은 예약부터 전송 시작까지 10초다 (§1.2).
    - 예약 대기 제한을 넘겨도 서버는 미전송이 확실할 때만 예약을 만료 취소한다.
    - 전송 여부나 실행 여부가 불명이면 서버는 예약을 취소하지 않는다. 서버는 격리와 복구 규칙을 따른다.
    - 서버는 서버 중단 시간을 예약 대기 시간에 포함한다 (FR-20).
  - 전송 중인 명령이 있으면 `begin_close`는 `conflict`와 `COMMAND_IN_PROGRESS`로 반납 시작을 보류한다.
- 인수 기준: 지표 3, 6
- 관련: FR-14, FR-18, NFR-03

### FR-20 기기별 종료·해제

- 범위: 서버
- 요구:
  - **대여형 점유 유지**
    - 모든 대여형 기기는 비콘 이탈 뒤에도 점유를 유지한다.
    - 대여시간을 초과해도 서버는 자동 반납하지 않는다. 서버는 점유를 유지하고 초과시간을 계산한다.
    - 시간 초과만으로 서버는 본인의 새 조작과 명시적 반납을 막지 않는다.
    - 새 조작에는 현재 허가, 근접, 접근 정책 검사를 계속 적용한다.
    - 추가금 부과는 구현 범위 밖이다.
  - **명시적 종료**
    - 본인의 유효한 해제 요청을 확인하면 서버는 기기와 점유 세션을 함께 `CLOSING`으로 바꾼다.
    - 서버는 반납을 `use_id`로 식별한다. 서버는 검사 시도마다 새 `check_id`로 기기에 반납 검사를 요청한다.
    - 기기가 물리 조건을 검사한다. 서버는 유효한 검사 결과와 점유 상태, 장애 상태로 종료를 결정한다.
    - 점유 세션은 생성 당시 `release_policy`와 함께 검사 기준의 ID와 버전을 보존한다. 서버는 검사 요청에 이 값을 담는다.
    - 검사 기준이 없는 점유 세션을 서버는 검사 통과로 추정하지 않는다.
    - 유효한 `not_ready`이면 서버는 `CLOSING`을 유지하고 새 `check_id`로 다시 검사한다. 재검사 대기 간격의 초기 기준은 1초다.
    - 서버는 문이 열린 정상 대기에 자동 종료 시간을 두지 않는다. 서버는 열린 시간이 길다는 이유만으로 격리하지 않는다.
    - 응답 기한 초과, 유효하지 않은 결과, `unknown`은 확인 불능이다. 검사 응답 기한의 초기 기준은 전송 시작부터 3초다.
    - 검사 시각의 나이가 안전 보고 허용 나이를 넘은 결과는 유효하지 않다.
    - 확인 불능이 연속으로 제한 시간 동안 이어지면 서버는 기기를 `FAULT`로 격리하고 점유를 보존한다. 제한 시간의 초기 기준은 30초다.
    - 유효한 `not_ready` 또는 `passed`만 확인 불능 타이머를 해제한다. 새 검사 발급과 오래된 보고 수신은 타이머를 초기화하지 않는다.
    - 기기가 `fault`를 보고하면 서버는 기기를 즉시 격리한다.
    - 서버는 새 검사 발급, 재접속, 새 장애로 무효가 된 이전 검사 결과를 종료 근거로 쓰지 않는다.
    - 유효한 `passed`이면 서버는 종료 가능 상태를 다시 검사한다. 서버는 세션 `CLOSED`, 기기 `AVAILABLE`, 종료 시각, 채택한 검사 근거와 종료 기록을 함께 반영한다.
    - 서버는 종료 저장의 완료를 확인한 뒤에만 반납 완료를 안내한다. 저장 결과가 불명이면 서버는 `use_id`로 반납 완료 기록을 조회한다.
    - 재시작 뒤 검사 대기 상태를 확실히 복원하지 못하면 서버는 새 검사를 요청한다.
    - 서버는 시간 값을 설정에서 받는다 (§1.2).
    - 검사 기준의 내용과 버전은 펌웨어 담당이 없는 동안 `architecture.md` §4 "반납 검사와 종료"의 개발 기준을 따른다 (#90). 실제 기기를 검증한 뒤 바꿀 수 있다.
    - 기기가 `AVAILABLE`이 되기 전에는 서버가 다음 방문자에게 허가하지 않는다.
    - 이미 `CLOSING`이면 서버는 비콘을 다시 수신해도 `ACTIVE`로 되돌리지 않는다.
    - 기기 이상과 실행 실패·불명은 점유 유지와 별개로 격리·복구 규칙을 따른다.
  - **공용형 기기**
    - 이 규칙은 점유 방식이 `shared`인 모든 기기에 적용한다. 시연 장비에서는 공용 조명, 무드등, 스피커다.
    - 서버는 점유 세션과 `CLOSING` 없이 공용형 기기의 상태를 바꾼다.
    - 유지 대상자는 켜기 요청에 성공했고 사용 권한이 유효한 계정이다. 횟수형 승인을 다 쓴 계정도 사용 권한이 유효하다 (#87).
    - 서버는 켜진 뒤 정해진 시간이 지나면 기기를 끄는 자동 타이머를 두지 않는다.
    - 서버는 유지 대상자마다 이탈을 판단한다. 유지 대상자가 한 명이라도 남으면 서버는 기기를 켜 둔다.
    - 유지 대상자가 모두 이탈하면 서버는 꺼짐을 요청한다. 서버는 전송 직전에 유지 대상자가 다시 생겼는지 확인한다.
    - 현재 접근 정책이 허용한 명시적 `off`는 다른 유지 대상자가 남아 있어도 서버가 허용한다.
    - 서버는 시간에 따른 자동 꺼짐과 이탈에 따른 꺼짐을 구분한다. 이탈에 따른 꺼짐은 구현과 검증을 마친 뒤 활성화한다.
    - 이탈 판단의 미수신 시간과 유예 시간은 초기 기본값 10초와 5초를 쓴다. 서버는 두 값을 설정으로 바꿀 수 있게 한다 (§1.2).
    - 유예 중 유효 재수신은 타이머를 초기화한다.
    - 이탈 판단은 같은 장소의 다른 앵커가 받은 본인 비콘의 유효 관측도 인정한다.
    - 같은 장소의 관측을 인정해도 새 조작의 허가·근접 검사는 유지한다.
  - **대여 기본 시간**
    - 대여 기본 시간의 초기 기준은 1시간이다 (§1.2). 대여 기본 시간은 초과시간 계산의 기준이다.
  - **재시작**
    - 서버는 서버 중단 시간을 예약 대기와 대여시간·초과시간 계산에 포함한다.
    - 서버는 기존 생성 시각과 기준 시각을 재시작 시각으로 바꾸지 않는다.
    - 재시작 뒤에도 서버는 대여시간 초과만으로 점유를 종료하지 않는다.
    - 서버는 서버 중단 중 비콘을 받지 못한 시간으로 이탈을 확정하지 않는다.
    - 서버는 공용형 기기의 유지 대상자를 복원하지 않는다. 재시작 뒤 켜기 요청에 성공한 계정만 새 유지 대상자가 된다.
    - 비콘이 보인다는 이유만으로 서버는 이전 유지 대상자를 복원하거나 새로 등록하지 않는다.
    - 서버는 복원과 현재 기기 상태 확인을 마치고 관측을 재개한 시점부터 초기 참여 대기를 둔다.
    - 초기 참여 대기는 이탈 판단의 미수신 시간과 유예 시간을 더한 시간이다. 초기 기준은 10초와 5초의 합이다 (§1.2).
    - 재시작 직후 유지 대상자가 없다는 이유만으로 서버는 공용형 기기를 끄지 않는다.
    - 초기 참여 대기가 끝났을 때 아래 조건을 모두 만족하면 서버는 꺼짐을 요청한다. 서버는 전송 직전에 유지 대상자가 다시 생겼는지 확인한다.
      - 새 유지 대상자가 없다.
      - 신선한 상태 보고로 켜짐을 확인했다.
      - 공용형 기기가 정상이다.
    - 새 유지 대상자가 생기면 서버는 계정별 미수신 시간과 유예 시간을 적용한다. 초기 참여 대기는 시간에 따른 자동 꺼짐 타이머가 아니다.
    - 방문자가 현장에 계속 있어도 재시작 뒤 새 켜기 요청이 없으면 초기 참여 대기 뒤 공용형 기기가 꺼질 수 있다. 이 동작은 유지 대상자를 복원하지 않는 선택의 결과다.
    - 오프라인, `FAULT`, 현재 상태를 확인하지 못한 기기에는 서버가 이 규칙만으로 새 명령을 보내지 않는다.
    - 대여형 점유 세션의 복원은 FR-19와 NFR-04를 따른다. 유지 대상자의 새 참여 기준을 대여형 점유 해제에 적용하지 않는다.
- 인수 기준: 지표 6
- 관련: FR-19, FR-21, NFR-04, NFR-12

### FR-21 핸들 소유권

- 범위: 서버
- 요구:
  - 서버는 조회 요청과 해제 요청에서 토큰 계정과 `use_id`의 소유권을 대조한다.
  - 대여시간 초과는 사용 권한 만료가 아니다. 초과 뒤에도 본인의 조작과 명시적 반납을 허용한다.
  - 새 조작에는 현재 허가, 근접, 접근 정책 검사를 계속 적용한다.
  - 서버는 본인의 점유 세션에만 재조작을 연결한다. 서버는 계정, 기기, 점유 세션의 연결을 저장 기록으로 검사한다.
  - 명시적 반납에는 본인 소유권과 안전 조건을 계속 적용한다.
  - 방문자는 보존기간 안에서 본인의 종료 이력을 조회할 수 있다.
  - 접근 승인 만료와 정책 변경의 새 조작 검사는 FR-14를 따른다. 승인 만료만으로 점유를 자동 반납하지 않는다.
  - 본인 종료 이력 조회 기간의 초기 기준은 종료 뒤 7일이다 (§1.2).
- 인수 기준: 지표 5
- 관련: FR-09, FR-14, FR-20

### FR-22 감사 로그·재현

- 범위: 서버
- 요구:
  - 서버는 아래 내용을 기록으로 남긴다.
    - 요청, 판정, 실행, 복구
    - 모델, 보정, 정책, 설정의 버전
    - 후보 확률. 다시 정규화하지 않은 사후확률이다 (FR-16).
  - 서버는 외부 `(계정, request_id)`를 전역 고유한 `internal_request_id`에 연결한다.
  - 서버는 내부 요청 ID로 계정별 외부 요청을 추적한다.
  - 서버는 같은 모델, 보정, 정책, 설정 값으로 판정을 재현한다.
  - DB는 판정 기록에 모델 파일의 버전을 보존한다. 근접 추정은 그 버전의 파일을 보존한다.
  - 서버는 내부 요청 행을 먼저 만들고, 그 뒤에 단계 로그를 연결한다.
  - 요청 행이 없는 사건은 별도 이벤트 ID와 NULL 요청 참조로 남긴다. 인증 실패가 한 예다.
  - **판정 기록**
    - 서버는 판정 한 건마다 판정 기록을 한 번 저장한다. 서버는 `ASK`, `BUSY`, `DENY`도 저장한다.
    - 판정 기록은 모델 버전, 보정 버전, 정책 버전, 적용한 설정, 후보별 사후확률, 관측 구간을 명시 필드로 담는다.
    - 근접 추정 전에 끝난 판정의 기록에는 모델 버전, 보정 버전, 관측 구간이 없다.
    - 같은 내부 요청 ID에 다른 판정이 다시 오면 서버는 기존 판정 기록을 덮어쓰지 않는다. 서버는 충돌로 거부한다.
    - 판정 기록의 충돌 검사는 내부 요청 ID로 한다. 외부 `request_id`의 중복 방지 보존기간은 이 검사를 바꾸지 않는다.
  - **감사 로그의 원본**
    - 감사 테이블이 감사 로그의 원본이다.
    - JSONL은 사본이다. 서버는 커밋한 감사 행을 커밋 순서대로 JSONL에 내보낸다.
    - JSONL 기록이 실패해도 서버는 판정과 실행을 막지 않는다. 서버는 감사 테이블에서 JSONL을 다시 만들 수 있다.
    - 서버는 같은 감사 이벤트 ID를 한 번만 저장한다.
  - 판정을 재현할 때 서버는 물리 명령을 다시 보내지 않는다.
  - 초기 구현은 명령 중복 방지 기록을 자동 삭제하지 않는다.
  - 기기는 새 명령의 대상 연결과 만료를 검사한다. 같은 명령은 기존 기록을 먼저 조회하고 재실행하지 않는다.
  - 서버는 결과 사건의 중복과 상충을 기록한다. 과거 결과는 현재 온라인·안전의 근거로 쓰지 않는다.
  - **이력과 감사 기록의 보존**
    - 본인 종료 이력 조회 기간의 초기 기준은 종료 뒤 7일이다. 상세 실행·감사 기록 보존의 초기 기준은 30일이다 (§1.2).
    - 서버는 진행 중이거나 미해결인 기록을 기간이 지났다는 이유만으로 지우지 않는다.
    - 이력·감사 기록의 보존과 중복 방지 보장기간은 구분한다. 이력·감사 기록이 남아 있어도 서버는 중복 방지 보장을 연장하지 않는다.
  - **외부 요청의 중복 방지 기록**
    - 서버는 요청의 최종 처리 완료 시점부터 20분 동안 외부 `(계정, request_id)`로 중복을 검사한다. 20분은 초기 기준이다 (§1.2).
    - 완료 뒤 20분이 지나면 서버는 요청 행의 외부 `request_id`를 비운다. 서버는 요청 행을 지우지 않는다.
    - 서버는 `internal_request_id`와 명령·점유·종료·감사 기록의 연결을 유지한다. 서버는 각 기록의 보존 기준에 따라 이력을 정리한다.
    - 진행 중이거나 미해결인 요청은 20분이 지나도 외부 요청 ID와 중복 검사 연결을 유지한다. 서버는 그 요청의 명령·점유·복구 연결 기록도 보존한다.
    - 외부 요청 ID를 비운 뒤에는 기존 요청과의 중복 방지 보장이 끝난다. 같은 외부 요청이 다시 오면 서버는 새 내부 요청 ID로 현재 조건을 검사한다.
    - 새 요청에도 서버는 현재 인증, 근접, 접근 정책, 점유 검사와 명령 연결·만료 검사를 적용한다.
    - 외부 요청의 재접수와 만료한 기존 물리 명령의 거부는 구분한다. 외부 요청 ID를 비워도 기기의 `command_id` 기록은 지우지 않는다.
  - **신규 조작 접수 제한**
    - 서버 전체의 중복 방지 항목 10만 건을 신규 조작 접수 제한의 초기 기준으로 둔다 (§1.2).
    - 서버는 중복 검사 연결을 유지한 요청의 항목과 명령의 중복 방지 항목을 각각 센다.
    - 외부 요청 ID를 비운 요청 행, 이력 보존만을 위해 남긴 행, 상세 감사 행은 세지 않는다.
    - 한도에 도달하면 서버는 완료 뒤 20분이 지난 요청의 외부 요청 ID를 비운다.
    - 정리한 뒤에도 한도 이상이면 서버는 새 물리 조작 요청을 `DENY`와 `CAPACITY_EXCEEDED`로 거부한다.
    - 서버는 ⓪에서 새 요청으로 확인한 요청에만 한도를 적용한다. 같은 요청의 재전송에는 한도와 관계없이 기존 결과를 반환한다.
    - 한도 이상이어도 서버는 진행 중인 작업의 결과 수신과 정산, 상태 조회, 반납, 복구를 계속한다.
    - 서버는 한도를 맞추려고 진행 중이거나 미해결인 기록을 지우지 않는다. 서버는 그 기록의 중복 검사 연결도 제거하지 않는다.
    - 10만 건은 신규 조작의 접수 기준이다. 결과·반납·복구 기록의 쓰기를 막는 절대 상한이 아니다.
    - 실제 저장 장애는 FR-19의 저장 오류 규칙을 따른다. 저장을 확인하지 못하면 서버는 완료와 재사용을 허가하지 않는다.
  - 미결: 명령 중복 방지 항목의 보존기간, 한도 도달 때의 정리 기준, 삭제 뒤 오래된 명령을 거부하는 방식. 실제 기기의 명령 기록 저장 방식을 검증한 뒤 정한다.
- 인수 기준: 지표 3, 5, 7
- 관련: NFR-13

### FR-23 전역 할당

- 범위: 서버
- 요구:
  - 서버는 **설정된 대기 구간 안에 들어온 `any:locker` 요청**을 묶는다. 대기 구간의 초기값은 500ms다.
  - 서버는 같은 근접 임계값, 정책, 점유 조건을 만족한 허용쌍에서 1:1로 배정한다.
  - 배정 기준의 우선순위는 아래와 같다.
    1. **배정 수를 최대화한다.**
    2. **비용 `−log(근접확률)`의 합을 최소화한다.**
    3. **ID 순서로 정한다.**
  - 근접확률은 다시 정규화하지 않은 사후확률이다 (FR-16). 비용 계산 방식은 그대로다.
  - 근접 확신이 부족하면 `ASK`다.
  - 점유나 경합으로 배정받지 못하면 `BUSY`다.
  - 인증이나 정책 검사에 실패하면 그 단계의 판정을 그대로 유지한다.
  - 서버는 전역 할당에서도 실행 직전 재검사를 한다.
  - 초기 임계값 0.95에서는 방문자마다 허용 후보가 많아야 하나일 수 있다. 그래서 전역 할당은 주로 충돌을 조정한다.
  - 서버는 배정 뒤 방문자가 이동한다고 가정해서 근접 조건을 완화하지 않는다.
  - 전역 할당은 `any:locker` 요청만 묶는다. 서버는 명시적 지정 요청의 임계값(FR-17)을 전역 할당에 적용하지 않는다.
- 인수 기준: 지표 9
- 관련: FR-18

### NFR-04 고장 격리·복구

- 분류: 신뢰성
- 요구:
  - 어느 상태에서든 이상을 감지하면 서버는 기기를 `FAULT`로 격리하고 후보에서 제외한다.
  - 검증된 `DEVICE_BUSY`의 접수·실행 전 거부는 이상이 아니다. 서버는 이 거부만으로 기기를 격리하지 않는다 (FR-19).
  - 무응답, 센서 이상, 안전 미확인이 생기면 서버는 불명확한 점유 세션을 보존한다.
  - 반납 검사의 유효한 `not_ready`는 이상이 아니다. 반납 검사의 격리 기준은 FR-20을 따른다.
  - 서버는 아래 순서를 마친 뒤에만 기기를 `AVAILABLE`로 복구한다.
    1. 기기별 안전을 확인한다.
    2. 서버 상태와 물리 상태를 동기화한다.
    3. 소유자가 복구를 승인한다.
  - 서버는 복구의 모든 과정을 기록한다.
  - 복구 재호출과 늦은 결과가 겹쳐도 서버는 중복 정산과 완료 상태의 되돌림을 막는다.
  - **복구 건**
    - 서버는 기기의 새 장애 격리마다 복구 건 하나를 만들고 고유한 `recovery_id`를 부여한다.
    - 서버는 복구 건을 기기, 관련 요청, 명령, 점유 세션과 연결해서 보존한다.
    - 서버는 실행 근거, 안전 근거, 물리 상태 동기화 근거, 복구 승인을 같은 복구 건에 연결한다.
    - 같은 미해결 장애의 재조회와 재시도는 같은 `recovery_id`를 쓴다. 새 근거나 결과가 와도 서버는 새 복구 건을 만들지 않는다.
    - 별개의 새 장애는 새 복구 건이다. 서버는 이전 복구 건의 복구 승인을 새 장애에 적용하지 않는다.
    - 근거 저장은 복구 정산이 아니다. 근거 저장만으로 서버는 승인 사용분, 점유, 기기 상태를 풀지 않는다.
    - 서버는 재시작하면 미완료 복구 건과 연결 기록을 복원한다. 서버는 현재 유효한 근거를 다시 확인한다.
  - **복구 준비 조회**
    - 서버는 복구 준비 조회와 복구 승인 요청을 따로 제공한다.
    - 복구 준비 조회는 준비 상태와 부족한 조건을 반환한다. 준비 상태는 `not_ready`, `ready`, `recovering`, `recovered`다.
    - 조회만으로 서버는 복구를 승인하지 않는다. 조회만으로 서버는 기기를 재사용 가능으로 바꾸지 않는다.
    - `ready`는 조회 시점에 조건을 갖췄다는 뜻이다. `ready`는 이후 실행의 허가가 아니다.
    - 복구 건이 없으면 서버는 `not_ready`와 `NO_RECOVERY_REQUIRED`를 반환한다. 조회는 새 복구 건을 만들지 않는다.
    - 서버는 다른 계정의 점유 정보를 외부 응답에 넣지 않는다 (NFR-08).
  - **복구 승인**
    - 복구 승인은 접근 승인(FR-14)과 별개다. 서버는 접근 승인을 복구 승인으로 쓰지 않는다.
    - 서버는 인증 결과로 승인 계정을 식별한다. 서버는 요청 본문의 계정 ID를 승인 주체로 쓰지 않는다.
    - 서버는 승인 요청 본문에서 안전 판정값과 정산 내용을 받지 않는다. 승인 시각은 서버가 기록한다.
    - 복구 승인은 안전 확인을 대신하지 않는다. 서버는 승인 요청을 받으면 아래 조건을 다시 검사한다.
      - 기기의 장소 소유권
      - 현재 복구 건
      - 미해결 명령 결과
      - 신뢰 상태와 온라인 여부
      - 최신 안전 근거와 물리 상태 동기화
    - 조건이 부족하면 서버는 거부 사유를 반환한다. 서버는 정산, 점유 해제, `FAULT` 해제를 하지 않는다.
    - 기기 재접속이나 새 장애로 기존 근거가 무효이면 서버는 새 유효 근거를 먼저 확인한다.
    - 서버는 같은 기기의 복구, 관측, 장애 반영을 한 번에 하나씩 순서대로 한다.
    - 승인 요청의 결과는 `completed`, `rejected`, `pending` 중 하나다.
    - 변경 없음이 확실한 저장 오류는 `rejected`와 `STORE_NOT_APPLIED`다. 서버는 복구 건을 유지한다.
    - 저장 응답이 불명이면 결과는 `pending`과 `STORE_OUTCOME_UNKNOWN`이다. 서버는 같은 `recovery_id`로 반영 결과를 조회한다.
    - 조회 결과가 없다는 이유만으로 서버는 미반영을 단정하지 않는다.
    - 완료한 복구 건을 다시 승인 요청하면 서버는 소유권을 확인한 뒤 기존 완료 결과를 반환한다.
  - **복구 정산**
    - 서버는 아래 다섯 가지를 한 트랜잭션에서 반영한다.
      1. 복구 승인 기록과 채택한 근거
      2. 승인 사용분 정산
      3. 대여형 점유 세션의 종료, 종료 시각, 종료 사유
      4. 기기의 복구 상태
      5. 감사 기록과 복구 건의 완료 결과
    - 공용형 복구에는 점유 세션을 만들거나 종료하지 않는다.
    - 서버는 확인 불가를 미실행으로 보지 않는다. 서버는 확인 불가만으로 승인 사용분을 반환하지 않는다.
    - 같은 복구 건에 같은 정산이 다시 오면 서버는 기존 완료 결과를 반환한다. 서버는 다시 정산하지 않는다.
    - 대상 연결이 다르면 서버는 충돌을 반환한다. 정산 내용이 상충하거나 예상 상태가 바뀌었을 때도 같다. 서버는 기록을 바꾸지 않는다.
    - 서버는 부분 정산을 완료로 반환하지 않는다.
    - 늦은 명령 결과가 정산 근거와 같으면 서버는 다시 정산하지 않는다. 상충하면 서버는 충돌 근거를 기록하고 다시 확인한다.
    - 늦은 결과로 서버는 종료한 점유 세션을 되살리거나 완료한 정산을 뒤집지 않는다.
    - 서버는 저장 반영을 확인한 뒤에만 재사용을 허가한다. 과거 복구의 완료는 현재 기기의 사용 가능 여부와 구분한다.
  - 복구 준비 조회와 복구 승인의 REST 경로는 상태 관리가 구현한다 (#89).
  - 미결: 나머지 관리 API의 구현 담당과 화면. 관리 API 담당을 배정한 뒤 정한다.
- 인수 기준: 지표 6
- 관련: FR-07, FR-19

### NFR-08 정보 최소화·통신

  - AI 호스트와 앱은 HTTPS와 토큰으로 인증한다.
  - 서버는 토큰 원문을 저장하지 않는다. 서버는 토큰의 SHA-256 해시를 소문자 hex 문자열로 저장한다. 해시에 솔트를 쓰지 않는다.
  - 서버와 기기는 폐쇄망과 기기별 자격정보로 인증한다. 서버는 기기별 자격정보를 검증한다.
  - MQTT 브로커는 익명 접속을 허용하지 않는다. 서버는 전용 계정을 쓰고 기기는 기기마다 다른 계정을 쓴다.
  - MQTT 브로커는 기기 계정에 자기 기기의 토픽만 허용한다.
  - 서버는 계정 정보와 점유 주체를 기기에 보내지 않는다.
- 인수 기준: 지표 7
- 관련: FR-01, FR-08, FR-11

### NFR-09 호스트 동등성

- 분류: 호환성
- 요구:
  - 3종 호스트의 판정과 결과는 98% 이상 일치한다.
  - 호스트를 바꿀 때 서버를 고치지 않는다.
- 인수 기준: 지표 7
- 관련: FR-10

### NFR-10 시연 장비

- 분류: 하드웨어
- 요구:
  - ESP32와 NimBLE
  - 저전압 모형 사물함 3개. 사물함은 서보와 리드 스위치를 쓴다.
  - LED 조명 3개
  - 스피커 1개. 스피커는 사물함, 조명과 같은 장소의 공용형 기기다.
  - 무드등 1개. 무드등은 두 번째 장소의 `light` 기능 공용형 기기다.
  - 앵커 8개. 기기마다 앵커가 하나다.
  - 디스펜서는 시연 장비에 넣지 않는다 (#61).
  - 유효 반경 약 0.5 m
- 인수 기준: 없음

- 같은 수집 회차의 RSSI 프레임은 서로 다른 데이터 분할에 섞지 않는다.
- 평가 스크립트는 관측에 저장한 수집 회차 ID로 학습·검증·시험 분할을 고정한다 (#41).
- 임계값은 검증셋에서만 고른다. 시험셋으로 확인하기 전에 임계값을 고정한다.
- 지표 3은 부하 스크립트로 비교한다. 지표 9는 기준 최적해와 비교한다.
- 결과가 0건이면 95% 신뢰구간 상한을 함께 적는다.
- 입력, 시나리오, 버전, 표본 수를 보존한다.
- 서버 범위의 FR마다 pytest 케이스를 둔다.
- 초기 호스트 연동은 `tools/list` 호출과 무해한 도구 호출로 확인한다.
- 대표 4장면을 50회 리허설하고 성공률과 실패 원인을 기록한다.
  - 세 기기 분리
  - 두 종류의 `BUSY`
  - 명시적 반납과 안전 확인 뒤 재사용
  - 호스트 교체
- 팀은 시연 시나리오를 현재 계약 안에서 구성한다. 시나리오에 맞춰 계약을 바꾸지 않는다 (#62).
  - 대여형 점유는 이탈로 풀리지 않는다. 시연은 명시적 반납과 안전 확인 뒤의 재사용을 보여 준다.
  - 서버가 `ASK`를 반환하면 방문자가 기기 앞으로 이동한다. 그다음 방문자가 다시 요청한다.
  - 소유자가 Android 앱에서 접근 요청을 승인한다.
  - 시연에는 AI 호스트가 발화의 맥락을 해석해서 도구와 `target_spec`을 고르는 장면을 넣는다.
  - AI 호스트의 해석은 허가의 근거가 아니다. 서버는 근접, 정책, 점유를 그대로 검사한다.
  - 기기마다 자리를 따로 둔다. 이웃 기기와 1 m 이상 떨어뜨린다.

| 발화 예 | AI 호스트의 도구 호출 |
|---|---|
| "짐 좀 맡길게" | `request_use`, `nearest:locker`, `open` |
| "좀 어둡네" | `request_use`, `nearest:light`, `on` |
| "아까 맡긴 거 꺼낼래" | `request_use`로 본인이 점유한 사물함을 다시 연다 |

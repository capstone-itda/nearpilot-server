## 1. 공통 규칙

### 1.1 범위와 지표 표기

- 범위: `서버` = 이 저장소가 구현하고 pytest 대상 / `연동` = 앱·노드·호스트가 주체이고 서버는 계약의 상대편만 구현 / `범위 밖` = 서버 구현 없음
- 인수 기준: §4 인수 기준 표의 지표 번호

### 1.2 수치 설정과 변경 원칙

- 본문의 근접 임계값(0.95/0.75), 관측 주기(약 1초), 이탈 판단(10초+5초), 할당 대기(500ms)는 **초기 기본값**이다. 코드 상수로 분산하지 않고 이름·단위·허용 범위가 있는 설정으로 관리한다. 값이 없는 타임아웃 등은 `미결`로 유지한다.
- 설정은 서버 기본값과 필요한 장치 종류/장치별 재정의로 관리한다. 판정 한 건에는 동일한 설정 버전을 적용하고, 실제 적용 값과 버전을 감사 기록에 보존한다. 변경 시 값의 범위와 관련 시간값의 일관성을 검증한다.
- 초기 변경 방식은 설정 파일·DB 수정 후 재시작으로 한다. 관측 처리·보정·HMM은 교체 가능한 인터페이스로 분리하고 모델·설정 묶음을 보존한다.
- 새 기본값은 신규 요청·세션부터 적용한다. 기존 승인의 만료·횟수와 진행 중 세션의 종료 정책·만료 시각은 생성 당시 값으로 유지한다. 현재 신뢰·온라인·안전 상태 검사는 계속 적용하고, 접근 정책 버전 변경 시 재승인 규칙도 유지한다.
- 모델과 결합된 임계값은 검증셋으로 함께 검증한다. §4의 성능 목표·표본 수는 평가 기준이며 운영 설정과 별도로 버전 관리한다. 팀 합의로 수정할 수 있지만 한 평가 회차 안에서는 고정하고 변경 전후 결과를 구분한다.
- 서버 인가·소유권 검사·중복 실행 금지·안전 확인 후 해제는 수치 조정으로 완화하지 않는다. API·상태·식별자·DB 관계 변경은 호환성 및 데이터 이전 검토를 거친다.

### 1.3 보존 데이터

| 보존 대상 | 필요한 정보·불변 조건 |
|---|---|
| 계정·비콘·장소 | 역할 `visitor/owner`, 토큰 해시 고유성, 활성 비콘과 계정 연결, `(uuid, major, minor)` 고유성, 장소 소유자 |
| 노드·장치 | 기능 `locker/light`, 점유 방식 `rental/shared`, 신뢰 `discovered/trusted/revoked`, 장소·상태·배타 그룹·해제 정책. 온라인은 `last_seen_at`과 TTL로 계산 |
| 정책·승인 | 공개 범위와 접근 모드, 정책 버전별 내용, 신청자·대상·승인 결과, 승인 사용분 예약·보류·소진 기록 |
| 요청·사용·명령 | 외부 `(계정, request_id)`·입력 요약, 내부 요청 ID·명령 ID, 계정·대상·동작·판정·사유·최대 확률·호스트, 세션·만료·종료 사유, 명령 전송·처리 기록. 대상 미확정이면 대상 ID는 NULL |
| 관측·감사 | 앵커·비콘·RSSI·프레임 시각·수집 라벨(장치 1~6 앞/none), 단계별 입력·결과, 후보 확률, 모델·보정·정책 버전, 임계값·관측 구간, 실행·종료·복구 |

데이터 관계는 아키텍처에 정의하며 테이블 수는 고정하지 않는다.

### 1.4 데이터 공개와 폐기

- 관측·로그는 평가 후 계정 ID를 제거한 공개용 데이터셋으로 보존한다.
- 토큰 해시와 비콘 식별자는 프로젝트 종료 시 폐기한다.

## 2. 기능 요구사항

FR-12B를 뺀 기능 요구사항은 모두 필수다.

### FR-01 계정·비콘 1회 연결

- 범위: 서버
- 요구:
  - 계정과 폰 iBeacon 식별자를 한 번 등록하고 토큰을 발급한다. 장소별 등록은 없다.
  - 다른 계정에 등록된 비콘 식별자는 거부한다.
- 인수 기준: 지표 5
- 관련: FR-08

### FR-02 비콘 백그라운드 송출

- 범위: 범위 밖 (앱)
- 요구:
  - 앱이 등록 식별자로 iBeacon을 계속 송출한다.
  - 앱은 비콘 송출 상태를 표시하고 중단을 감지한다.
- 인수 기준: 지표 4, 7
- 관련: NFR-12

### FR-03 소유자 승인

- 범위: 서버 (UI는 앱)
- 요구:
  - 제한 장치의 승인 요청 목록을 제공하고, 권한 있는 소유자의 승인·거부를 즉시 반영한다.
  - 대기 승인이 생기면 소유자 앱에 알리고, 알림 전달 여부와 무관하게 대기 목록에 남긴다.
  - 소유자는 승인 요청 알림을 눌러 Android 앱의 해당 요청 화면에서 승인·거부한다. 웹·AI 호스트 화면으로 보내지 않는다.
  - 앱은 결정만 전달하며 승인 권한·대기 상태·정책 버전 검증과 기록은 서버가 한다.
  - 승인 결과는 기존 MCP 도구 계약으로만 다룬다. 방문자가 다시 요청하면 호스트가 `request_use`를 호출하고, 서버는 ⓪~⑥을 처음부터 적용해 ④에서 유효 승인을 확인한다. 아직 대기 중이거나 재승인이 필요하면 `NEED_APPROVAL`을 반환하고 사유로 대기·거부·만료를 구분한다.
  - 미결: 독립 AP에서 소유자 앱으로 알리는 수단(앱 연결 유지·주기 조회·FCM 등 후보. FCM은 인터넷 연결이 필요해 미채택)
  - 미결: 소유자 단말이 AP 밖에 있을 때의 처리
  - 미결: 대기 승인의 만료·중복 요청 처리
  - 미결: 방문자에게 결과를 알릴지 여부
- 인수 기준: 지표 5
- 관련: FR-14

### FR-04 기능 발표(발견)

- 범위: 연동
- 요구:
  - 노드가 부팅 시 기능·점유 방식을 MQTT `announce`(retained)로 발표하고 서버가 발견한다.
- 인수 기준: 지표 5
- 관련: FR-13

### FR-05 RSSI 보고

- 범위: 연동
- 요구:
  - 노드가 약 1초 간격으로 (비콘 식별자, RSSI)를 `rssi`로 보고하고 서버가 수신한다.
- 인수 기준: 지표 8

### FR-06 서버 허가 후 실행

- 범위: 연동
- 요구:
  - 노드는 서버의 `OK!(command_id)`를 받은 경우에만 구동하고, 서버는 허가한 명령만 `cmd`로 보낸다.
  - 서버는 물리 명령마다 고유 `command_id`를 발급한다. 노드 명령·결과·중복 방지는 `command_id`로 연결한다.
- 인수 기준: 지표 3, 5
- 관련: FR-18, FR-19

### FR-07 실행·안전 상태 보고

- 범위: 연동
- 요구:
  - 노드가 실행 결과(`result`)·안전 상태(`status`)를 보고한다. 결과 불명·안전 미확인은 FAULT로 격리한다.
  - 서버는 실행 결과를 확인한다. 시간 초과·연결 끊김은 실행 성공으로 처리하지 않는다.
  - 미결: 실행 응답 대기 제한 시간
  - 미결: 장치별 안전 센서 조합
  - 미결: 실행 여부 확인 근거
- 인수 기준: 지표 6
- 관련: NFR-04

### FR-08 통합 MCP 엔드포인트

- 범위: 서버
- 요구:
  - 서버는 `/mcp`에 MCP Streamable HTTP를 직접 제공하고 같은 프로세스에서 토큰 식별과 판정을 처리한다.
  - 토큰을 검증한다. 토큰 없는/무효 호출은 거부한다.
- 인수 기준: 지표 7
- 관련: FR-01, NFR-11

### FR-09 MCP 도구 6개

- 범위: 서버
- 요구:
  - 서버는 아래 도구 6개를 제공한다.
  - `target_spec`은 근접 지정(`nearest:locker`), 명시적 지정(`locker-1`), 허용 후보 중 배정(`any:locker`)을 지원한다. 동작은 `open`·`on`·`off`를 지원한다.
  - 재질문·승인 후 사용 재요청은 새 `request_id`를 사용하고 원래 요청/승인과 연결한다. 같은 요청의 전송 재시도는 기존 ID를 유지한다.
  - 응답에는 판정·사유·장치 정보·본인 요청/사용 핸들을 담는다.
- 인수 기준: 지표 7
- 관련: FR-10, FR-11, FR-21

| 도구 | 계약 |
|---|---|
| `find_available_devices` | 근접·신뢰·온라인·사용 가능·미점유 후보를 '조작 가능'과 '승인 필요'로 구분. 비공개 장치·점유 주체 비노출, 비콘 미수신이면 빈 목록 |
| `get_device_state` | 근접 검사 없이 장치 상태 조회. 공개 장치는 유효 토큰, 비공개 장치는 소유자 또는 현재 본인 사용 세션 권한 필요. 점유 주체 비노출 |
| `request_access` | 제한 장치에 대한 접근 승인 요청. 승인 요청 자체가 실행 허가는 아님 |
| `request_use` | `target_spec`, 동작, `request_id`로 사용 요청. 중복·근접·정책·점유 검사 후 실행 |
| `release_use` | 본인 `use_id`의 사용 종료 요청. 유효한 사용 권한과 장치의 해제 정책·안전 상태를 확인 |
| `get_use_status` | 근접 검사 없이 본인 세션·종료 이력 조회. 사용 권한이 만료돼도 이력 보존기간 내 조회 가능하며 타인 핸들은 거부 |

- 인수 기준: 없음

### FR-13 노드 신뢰·온라인 판정

- 범위: 서버
- 요구:
  - 신뢰와 온라인을 분리 관리하고 trusted + ONLINE + 비FAULT 장치만 후보로 삼는다. 미신뢰·오프라인·FAULT는 후보에서 제외한다.
  - 온라인은 `last_seen_at`과 TTL로 계산한다.
  - 미결: 온라인 TTL
- 인수 기준: 지표 5
- 관련: FR-04

### FR-14 장치별 접근 정책·승인

- 범위: 서버
- 요구:
  - 장치별 정책 설정과 접근 요청을 제공한다. 승인 여부는 사용 시 서버가 검사한다.
  - 접근 정책은 `open`(개방) / `restricted`(승인 필요)다.
  - 승인은 **요청자·장치·동작·정책 버전**에 묶고 승인 권한 계정만 처리한다.
  - 사물함은 기본 `one_time`으로 실행 후 소진, 조명은 `time_window`로 유효기간 내 반복 허용하며 횟수·유효시간을 장치별 설정한다.
  - 거부·만료·정책 변경 시 재승인이 필요하고, 횟수 초과·다른 동작은 거부한다. 정책 변경은 진행 중 점유에 소급하지 않는다.
  - 공개 범위 `public/private`는 승인 필요 여부와 별도로 관리한다. 비공개 장치는 주변 목록에서 숨기고, 과거 사용 이력은 해당 세션 기록의 조회만 허용한다.
  - 접근 정책은 버전별 내용을 보존하며 운영 설정 버전과 분리한다. 운영 수치만 변경했다고 기존 승인을 무효화하지 않는다.
  - 미결: 승인 기본 유효시간
- 인수 기준: 지표 5
- 관련: FR-03, FR-19

### FR-15 계정–비콘 대조

- 범위: 서버
- 요구:
  - 토큰 계정의 등록 비콘이 해당 장소 앵커에서 최근 T초 이내 수신됐을 때만 판정을 진행한다(①). 원격 요청·관측 부재는 `DENY`다.
  - 미결: 비콘 최근 수신 T
- 인수 기준: 지표 4, 5
- 관련: FR-18

### FR-16 근접 추정·대상 선택

- 범위: 서버
- 요구:
  - 앵커별 RSSI에 관측 모델 + HMM을 적용해 사후확률 최대 장치를 선택한다(③).
  - 미결: 관측 특징·수집 라벨·결측 처리·HMM 상태/전이·보정 방법
- 인수 기준: 지표 1, 8
- 관련: FR-17, NFR-02, NFR-06

### FR-17 비용 기반 재질문

- 범위: 서버
- 요구:
  - 사후확률이 설정 임계값(초기 사물함 0.95·조명 0.75) 미만이면 실행 없이 `ASK`를 반환한다.
  - 명시적 지정도 근접 확률이 임계값 미만이면 실행하지 않고 이동을 안내한다.
  - 근접 임계값 조정은 검증셋에서만 수행하고 시험셋 평가 전에 고정한다.
  - 미결: 오류 비용
- 인수 기준: 지표 2
- 관련: FR-16

### FR-18 결정론적 판정 순서

- 범위: 서버
- 요구:
  - 인증·입력 검증 후 아래 순서를 적용한다. **기본값은 거부**다. 공용형의 점유 검사 생략 외에는 호스트나 사용자 발화로 단계를 생략할 수 없다.
  - 판정은 `OK`(허가), `BUSY`(장치/사용자 점유 충돌), `ASK`(재질문), `DENY`(거부), `NEED_APPROVAL`(승인 필요)다.
  - 비허가 요청은 기기를 실행하거나 새 점유를 유지하지 않는다.
  - **실행 직전 허가·근접·대상을 재검사**하고 자기 요청의 예약은 타인 점유로 간주하지 않는다.
  - 공용 조명은 ⑤⑥과 점유 세션 생성을 건너뛰지만 승인 사용분은 원자적으로 확보한다.
  - 실행 확인 전에는 호스트에 완료를 안내하지 않는다.
  - 대표 흐름: `request_use(nearest:locker, open, request_id)` → 계정 식별·내부 ID 연결 → ⓪~⑥·승인 사용분 확보 → `RESERVED` → 실행 직전 재검사 → 노드에 `OK!(command_id)` → 실행 확인·승인 소진 → `ACTIVE`·`use_id` → 완료 안내
- 인수 기준: 지표 3, 4, 5
- 관련: FR-15, FR-16, FR-17, FR-19

| 순서 | 검사와 결과 |
|---|---|
| ⓪ 중복 | `(계정, request_id)`와 정규화한 입력을 대조. 같으면 기존 결과·진행 상태 반환, 같은 키의 다른 입력은 충돌로 거부. 다른 계정의 결과는 반환하지 않음 |
| ① 비콘 | 토큰 계정의 등록 비콘이 해당 장소 앵커에서 최근 T초 이내 수신됐는지 검사. 원격 요청·관측 부재는 `DENY` |
| ② 후보 | 신뢰·온라인·요청 종류가 맞고 FAULT가 아닌 장치로 구성. 정책·점유 때문에 다른 물리적 대상이 선택되지 않도록 정책·점유 검사는 대상 확정 후 ④~⑥에서 수행 |
| ③ 근접 | 앵커별 RSSI에 관측 모델 + HMM을 적용해 사후확률 최대 장치를 선택. 설정 임계값(초기 사물함 0.95·조명 0.75) 미만이면 실행 없이 `ASK` |
| ④ 정책 | 장치 정책과 접근 승인을 검증. 승인이 필요하면 `NEED_APPROVAL`, 정책상 허용되지 않으면 `DENY` |
| ⑤ 장치 점유 | 배타적 장치가 이미 점유 중이면 장치 사유의 `BUSY` |
| ⑥ 사용자 점유 | 같은 `exclusive_group`에서 이미 다른 장치를 점유하면 사용자 사유의 `BUSY`. ⑤⑥ 검사와 예약 생성은 한 트랜잭션으로 처리 |

### FR-19 원자적 점유·상태 머신

- 범위: 서버
- 요구:
  - **원자성·멱등성:** SQLite 단일 쓰기 경로와 `BEGIN IMMEDIATE`로 장치·사용자 점유 확인 및 `RESERVED` 생성을 묶는다. 동시 요청·재전송에도 이중 점유와 중복 물리 실행을 방지해야 한다. 서버 기록과 노드의 중복 실행 방지 계약을 함께 정의한다.
  - **승인 사용분:** 실행 전에 요청별 사용분을 원자적으로 예약하고 잔여 횟수에서 제외한다. 대여형은 점유 예약과 같은 트랜잭션에서 처리한다. 성공 확인 시 소진 확정, 재검사 실패 등 명령 미전송이 확실한 경우에만 자동 반환한다. 전송 후 결과 불명은 승인 사용분·점유를 보류하고 복구 후 실행 여부에 따라 정산한다.
  - **장애·재전송:** 서버와 노드는 명령·처리 기록을 재시작 후에도 보존하고 같은 `command_id`를 다시 실행하지 않는다. 전송 시도 후 응답 유실·재시작으로 실행 여부가 불명확하면 새 명령으로 재시도하지 않고 FAULT 복구한다. 기록만으로 실행 여부를 확정하지 못하면 물리 상태 확인까지 신규 허가를 차단한다.
  - **대여형 사물함:** 장치는 `AVAILABLE → RESERVED → ACTIVE → CLOSING → AVAILABLE`. 실행 확인 시 `ACTIVE`와 계정·장치·만료에 묶인 `use_id`를 발급한다. 점유 세션은 `RESERVED → ACTIVE → CLOSING → CLOSED`이며 종료 사유는 `release / leave / timeout / fault`다.
  - 미결: 예약 대기 제한 시간
- 인수 기준: 지표 3, 6
- 관련: FR-14, FR-18, NFR-03

### FR-20 장치별 종료·해제

- 범위: 서버
- 요구:
  - **종료:** 명시 해제·대여 타임아웃·비콘 연속 미수신과 유예 만료(초기 **10초 미수신+5초 유예**) 시 `CLOSING`. `release_policy`의 안전 상태 확인 후 세션을 `CLOSED`, 장치를 `AVAILABLE`로 바꾼다. 그 전에는 다음 사용자에게 허가하지 않는다.
  - **이탈 취소:** 유예 중 유효 비콘이 다시 수신되면 이탈 타이머를 초기화한다. 이미 `CLOSING`에 진입했으면 비콘 재수신만으로 `ACTIVE`로 되돌리지 않고 안전 확인·종료를 계속한다.
  - **공용 조명:** 점유·`CLOSING` 없이 상태를 변경한다. 이탈 시 자동 꺼짐은 초기 비활성으로 두며, 다중 사용자 유지 기준을 정한 뒤 `release_policy`로 활성화한다.
  - 미결: 대여 기본 타임아웃
  - 미결: 조명 자동 꺼짐을 활성화하기 전의 다중 사용자 유지 기준·시간. 초기 비활성 구현은 이 결정에 의존하지 않는다.
- 인수 기준: 지표 6
- 관련: NFR-12

### FR-21 핸들 소유권

- 범위: 서버
- 요구:
  - 조회·해제는 토큰 계정과 `use_id` 소유권을 대조한다.
  - 만료된 사용 권한으로 추가 조작·해제할 수 없지만 본인 종료 이력은 보존기간 내 조회할 수 있다.
  - 만료 후 안전 종료는 서버가 수행한다.
  - 미결: 본인 종료 이력의 보존기간
- 인수 기준: 지표 5
- 관련: FR-09

### FR-22 감사 로그·재현

- 범위: 서버
- 요구:
  - 요청·판정·실행·복구와 모델·보정·정책·설정 버전, 후보 확률을 기록으로 남긴다.
  - 서버는 외부 `(계정, request_id)`를 전역 고유 `internal_request_id`에 연결한다.
  - 판정은 내부 요청 ID로 외부 계정별 요청을 추적하고 동일한 모델·보정·정책·설정 값으로 재현한다.
  - 내부 요청 행을 먼저 만든 후 단계 로그를 연결한다. 인증 실패 등 요청 행이 없는 사건은 별도 이벤트 ID와 NULL 요청 참조로 남긴다.
  - 재현 시 물리 명령을 재전송하지 않는다.
  - 미결: 멱등 키·서버/노드 명령 기록의 보존기간과 저장 용량
  - 미결: 기록 삭제 뒤 오래된 요청·명령을 재실행하지 않는 만료/거부 계약
- 인수 기준: 지표 3, 5, 7
- 관련: NFR-13

### FR-23 전역 할당

- 범위: 서버
- 요구:
  - **설정된 대기 구간(초기 500ms) 내 `any:locker` 요청**을 묶는다.
  - 동일한 근접 임계값·정책·점유 조건을 만족한 허용쌍에서 **배정 수 최대화 → 비용 `−log(근접확률)` 합 최소화 → ID순**으로 1:1 배정한다.
  - 근접 확신 부족은 `ASK`, 점유·경합으로 미배정되면 `BUSY`, 인증·정책 실패는 해당 판정을 유지한다. 실행 직전 재검사도 수행한다.
  - 초기 0.95 기준에서는 사용자당 허용 후보가 최대 하나일 수 있어 충돌 조정 중심으로 동작하며, 배정 후 이동을 전제로 근접 조건을 완화하지 않는다.
- 인수 기준: 지표 9
- 관련: FR-18

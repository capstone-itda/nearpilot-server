# 한국어 STE 규칙

ASD-STE100을 한국어에 맞게 바꾼 규칙이다. intent 본문과 PR 본문 중 새로 쓴 문장에 적용한다.
섹션 제목(영어)과 "주고받는 것" 표의 "코드상 이름" 열은 예외다.
`[검사]`가 붙은 규칙은 `intent_tool.py check`가 검사한다. 나머지는 맨 아래 점검표로 확인한다.

## 1. 단어

**1-1. 한 개념에는 한 용어만 쓴다.** `[검사: 기기, 디바이스]`
- 표기는 PRD를 따른다.
- 사물함·조명처럼 사용하는 대상은 "장치"로 쓴다.
- ESP32 보드나 MQTT 메시지를 주고받는 주체를 말할 때만 "노드"로 쓴다.

**1-2. 용어가 처음 나올 때 뜻을 적는다.** 두 번째부터는 용어만 쓴다.
- 짧으면 용어 뒤에 붙여 괄호로 적는다. 예: 비콘(블루투스 신호)
- 일반 기술 용어는 일반적인 뜻을 출처 없이 적는다.
- 팀 공통 용어(계층·역할 이름)는 풀지 않는다.
- 근거에 뜻이 없는 프로젝트 용어는 뜻을 짐작하지 않는다. 쓰지 않거나 Open questions로 보낸다.

**1-3. 쉬운 말을 쓴다.** `[검사]`

| 쓰지 않는다 | 쓴다 |
|---|---|
| 수행한다, 진행한다 | 한다 (또는 구체적인 동사) |
| 상이하다 | 다르다 |
| 기인한다 | ~때문이다 |
| 활용한다 | 쓴다 |
| 존재한다 | 있다 |
| 상기 | 위 |
| 해당 ~ | 대상 이름 |
| ~에 대하여, ~에 대해 | ~를, ~에 |
| ~를 통해 | ~로 |
| ~하도록 한다 | ~한다 |

**1-4. 코드상 이름은 "주고받는 것" 표의 마지막 열에만 쓴다.** `[검사: 대소문자가 섞인 이름, 클래스.함수]`
- 판정 결과(`OK`, `ASK` 등), 상태값(`RESERVED` 등), 식별자(`request_id`, `use_id`), 대상 지정(`nearest:locker`)은 본문에 쓸 수 있다.
- 출처 괄호 안의 `shared:` 이름은 예외다.

**1-5. 독자가 새로 배워야 하는 용어는 5개 이하로 쓴다.** `[검사: 용어 뒤에 붙인 괄호 풀이 수]`

## 2. 명사구

**2-1. 명사를 셋 넘게 잇지 않는다.** 조사나 동사로 푼다.
- 나쁨: 승인 사용분 예약 상태 전이
- 좋음: 승인 사용분의 예약 상태가 바뀐다

## 3. 동사

**3-1. 능동태로 쓰고 주어를 밝힌다.**
- 나쁨: 요청이 거부된다.
- 좋음: 서버가 요청을 거부한다.

**3-2. 현재형 "-다"체로 쓴다.** PR 본문에서 리뷰어에게 부탁하는 문장만 "~해 주세요"로 쓴다.

**3-3. 추측 표현을 쓰지 않는다.** "~일 것이다", "~로 보인다", "~할 수도 있다"
- 권한이나 능력을 말하는 "~할 수 있다"는 쓴다. 예: "소유자는 승인할 수 있다."

**3-4. 규칙은 "~한다 / ~하지 않는다"로 단정한다.**

## 4. 문장

**4-1. 한 문장에는 한 주제만 쓴다.** 연결어미(-고, -며, -지만, -는데, -므로)로 절을 잇지 않는다.
- 조건이나 이유 하나와 주절 하나까지는 한 문장에 쓴다. 예: "관측이 없으면 서버는 거부한다."

**4-2. 설명 문장은 15어절 이하로 쓴다.** `[검사]`

**4-3. Constraints의 문장은 12어절 이하로 쓴다.** `[검사]`
- 어절은 띄어쓰기로 나뉜 덩어리다.
- 출처 괄호, 담당자 괄호, 링크 주소는 세지 않는다.

**4-4. 주어와 목적어를 생략하지 않는다.** "이것", "그것"은 가리키는 대상이 바로 앞 문장에 있을 때만 쓴다.

## 5. 문단과 분량

**5-1. 문단의 첫 문장에 핵심을 쓴다.**

**5-2. 문단 하나에는 주제 하나만 쓴다. 6문장 이하로 쓴다.** `[검사]`

**5-3. 조건·단계·항목이 셋 이상이면 세로 목록으로 쓴다.** 순서가 있으면 번호 목록을 쓴다.

**5-4. 문서 본문은 600어절 이하로 쓴다.** `[검사: 표, 출처, 담당자 괄호 제외]`

## 6. 근거

**6-1. 사실 문장 끝에 출처를 붙인다.** `[검사: 형식, 절 번호와 shared 이름이 있는지]`
- 형식: `(PRD §3)`, `(PRD §2·§3)`, `(PRD 부록 A)`, `(architecture §4)`, `(shared: ProximityResult)`, `(shared: ProximityEstimator.posterior)`
- 여러 개면 쉼표로 잇는다. 예: `(PRD §3, architecture §4)`
- Problem의 장면 묘사와 그 결과, 일반 기술 용어의 뜻에는 출처를 붙이지 않아도 된다. 수치와 요구 조건에는 반드시 붙인다.

**6-2. "보장하는 것", "보장하지 않는 것", Constraints의 항목에는 반드시 출처를 붙인다.** `[검사]`

**6-3. Open questions의 항목은 `<질문>? (<역할> @<ID>)` 형식으로 쓴다. 괄호에는 답할 담당자를 적는다.** `[검사]`
- 담당자가 여럿이면 쉼표로 잇는다. 예: `(판정 @eunji719, 상태 관리 @JM-220)`
- 담당자가 없는 영역은 `(<폴더> 담당 미정)`으로 쓴다.
- 질문이 없으면 `- 없음.`으로 쓴다.

## 점검표

- [ ] 모델, 알고리즘, 파라미터, 데이터 수집, 평가 절차, 테스트를 쓰지 않았다
- [ ] 문장마다 "지우면 독자가 무엇을 못 하게 되나?"에 답이 있다
- [ ] 같은 대상을 두 가지 말로 부르지 않았다 (1-1)
- [ ] 처음 나온 용어마다 뜻을 적었다. 근거에 없는 뜻을 짐작하지 않았다 (1-2)
- [ ] 명사를 셋 넘게 이은 곳이 없다 (2-1)
- [ ] 행위자가 있는 수동형("~된다", "~되어진다")을 능동형으로 바꿨다 (3-1)
- [ ] 추측 표현이 없다 (3-3)
- [ ] 조건·이유 하나와 주절 하나를 넘게 이은 문장이 없다 (4-1)
- [ ] 지시어가 가리키는 대상이 분명하다 (4-4)
- [ ] 숫자, 순서, 개수, 문장의 주어를 출처와 하나씩 대조했다
- [ ] 출처 절에 그 내용이 실제로 있다 (6-1)

# intent

양식은 `template.md`, 문장 규칙은 `style.md`, 검사는 `intent_tool.py`를 쓴다. 모두 이 파일과 같은 폴더에 있다.

## 공통 규칙

- 경로는 저장소 루트 기준이다.
- 셸 명령은 `git`, `gh`, `python`만 쓴다. 한 번에 하나씩 실행한다. `&&`, `;`, 파이프로 잇지 않는다. 파일은 파일 읽기 도구로 읽는다.
- Python은 `python3`, `python`, `py` 순서로 찾는다. 아래의 `python`을 찾은 명령으로 바꾼다.
- 근거는 `docs/prd.md`, `docs/architecture.md`, `server/src/nearpilot/shared/`만 쓴다. shared와 문서가 다르면 문서를 따른다. 문서가 미결로 둔 값은 shared에 있어도 쓰지 않는다.
- 근거에 없는 내용과 새 결정은 쓰지 않는다.
- 다른 intent는 `status` 출력만 본다. 본문은 갱신·수정 대상만 읽는다.
- 주제가 작성자의 담당 범위 밖이면 경고한다. 작성자가 계속하라고 할 때만 진행한다.
- PR에는 `docs/intent/{slug}.md` 하나만 넣는다.
- push 전에 작성자의 확인을 받는다. main에는 push하지 않는다.

## 문서 내용 규칙

독자는 이 영역을 모르는 다른 담당자다. 독자가 이 영역이 무엇을 하는지, 자기 일과 맞물리는 부분이 무엇인지 알면 된다.

- 영역을 블랙박스로 쓴다. 무엇을 받고 무엇을 내놓는지만 쓴다. 모델, 알고리즘, 내부 파라미터, 데이터 수집, 평가 절차, 테스트는 쓰지 않는다. PRD가 요구사항으로 적은 기준값(예: 임계값의 초기값)은 쓴다.
- 이웃 영역의 일은 쓰지 않는다. 경계에서 누가 무엇을 넘기는지만 한 줄로 쓴다. 예: "판정이 후보 장치 목록을 넘긴다."
- 문장마다 묻는다: "이 문장을 지우면 독자가 무엇을 못 하게 되나?" 답이 없으면 지운다.
- 전문 용어 대신 그 용어가 가리키는 것을 쉬운 말로 쓴다. 예: "사후확률" → "방문자가 이 장치 앞에 있을 확률"
- 헤더의 Requirements에는 ID를 줄이지 않고 쉼표로 나열한다. 예: `Requirements: FR-16, FR-17.` PR 제목에서만 `FR-16·17`처럼 줄인다.

섹션별로 쓸 것:

- **Problem:** 사용자가 겪는 한 장면과 그 비용. 근거에 없는 배치나 수치는 지어내지 않는다.
- **Proposed outcome:** 이 영역이 받는 것 → 하는 일 → 내놓는 것만 순서대로. "확인 방법"에는 PRD §6 지표 중 독자가 뜻을 바로 아는 것의 결과 기준만 쓴다. 비교 기준이 미결인 지표와 시험 조건은 쓰지 않는다.
- **Affected users and systems:**
  - 상대는 받는 값을 만드는 담당자와 넘기는 값을 쓰는 담당자다. architecture §4 계약 표, `shared/interfaces.py`의 구역 주석, architecture §1 담당 코드로 찾는다.
  - 계층 안의 어느 역할인지 근거로 정할 수 없으면 `CORE (역할 미정)`처럼 쓰고 Open questions에 적는다. 중간에서 전달하는 쪽이 정해지지 않았을 때도 Open questions에 적는다.
  - 상대 역할의 intent가 main에 있으면 상대 칸에 링크한다. 예: `판정 (@id, [intent](core-x.md))`
  - 상대에게 영향을 주는 성질은 근거의 진술에 따라 나눈다. shared의 docstring과 주석도 근거의 진술이다.

    | 근거의 진술 | 넣는 곳 |
    |---|---|
    | 항상 그렇다 | 보장하는 것 |
    | 그렇지 않다고 명시하거나, 받는 쪽에 다시 검사하라고 한다 | 보장하지 않는 것 |
    | 말이 없다 | Open questions |

  - 받아 쓰는 상대가 없으면 "주고받는 것", "보장하는 것", "보장하지 않는 것"을 지운다.
- **Constraints:** 이 영역이 지키는 규칙 중 다른 담당자도 알아야 하는 것만. 이웃 영역의 규칙과 Affected에 쓴 내용은 쓰지 않는다.
- **Open questions:** 작성자 혼자 답할 수 없는 질문만. `- <질문>? (<역할> @<ID>)` 형식으로 답할 담당자를 적는다. 여럿이면 쉼표로 잇는다. 담당자가 없는 영역은 `(<폴더> 담당 미정)`으로 쓴다. 팀 전체가 정할 값(PRD §7)은 그 값을 쓰는 담당자를 적는다.

## 흐름

### 1. 준비

1. `git status --porcelain` 출력이 있으면 멈춘다. 작성자에게 커밋이나 stash를 요청한다.
2. `git branch --show-current`로 지금 브랜치를 기억한다.
3. `git fetch origin` 후 `git switch --detach origin/main`.
4. `gh api user --jq .login`으로 작성자를 확인한다. 실패하면 작성자에게 GitHub ID를 묻는다.
5. architecture §1 역할 표에서 작성자의 역할과 담당 코드를 찾는다.
6. `python .claude/skills/intent/intent_tool.py status`

### 2. 주제와 모드

작성자가 주제나 요구사항 ID를 주면 그것을 쓴다. 주지 않거나 무엇을 써야(구현해야) 하는지 물으면 주제를 제안한다.

1. architecture §2 폴더 주석에서 작성자의 담당 폴더에 붙은 FR·NFR을 모은다. 작성자가 계층 전체를 맡았으면 §1 계층 표의 "관련 요구사항" 열도 쓴다. PRD 부록 A의 "서버 범위"가 "범위 밖"인 FR과 주고받는 것이 없는 NFR은 뺀다.
2. `status`와 대조해 ID마다 `완료`(main에 있음), `작성 중`(열린 PR), `없음`을 표시한다.
3. `없음`인 ID를 1~3개씩 묶어 후보 2~4개를 만든다. 한 ID는 한 후보에만 넣는다. 후보마다 slug, ID, 쉬운 말 한 줄, 받아 쓰는 담당자를 적는다.
4. 작성자의 역할이 제공하는 shared 인터페이스를 다루는 후보를 앞에 둔다.
5. 진행표와 후보를 보여주고 작성자가 고르게 한다.

slug는 `{계층}-{요약}`이다.

- 계층: 주제의 담당 폴더가 속한 `api`, `core`, `db`, `iot`, `shared` 중 하나. `tools/` 아래 도구는 그 도구가 돕는 계층.
- 요약: 주제를 나타내는 영어 1~3단어. 영문 소문자·숫자·하이픈.

"같은 주제"는 slug가 같거나 요구사항 ID가 겹치는 것이다. 일부만 겹치면 작성자에게 묻는다.

| 상황 | 모드 | 브랜치 |
|---|---|---|
| 같은 주제의 열린 PR을 작성자가 올렸다 | PR 수정 | `git switch intent/{slug}` 후 `git pull --ff-only` |
| 같은 주제의 열린 PR을 다른 사람이 올렸다 | 멈추고 그 PR을 알린다 | — |
| main에 같은 slug의 문서가 있다 | 갱신 | `git switch -c intent/{slug}` |
| 그 밖 | 새로 쓰기 | `git switch -c intent/{slug}` |

같은 이름의 로컬 브랜치가 이미 있으면 멈추고 작성자에게 묻는다.

### 3. 근거 읽기

- PRD: 부록 A의 해당 ID 행, 그 행의 § 열이 가리키는 본문, §6의 해당 지표, §7의 관련 미결 항목.
- architecture: §1~§5, 그리고 §6·§9의 관련 행.
- shared: 주제가 제공하거나 쓰는 Protocol과 그 모델·열거형·docstring.

### 4. 먼저 설명

작성자가 원하지 않으면 건너뛴다.

1. 작성자에게 주제를 설명한다. 내부 방식(모델, 알고리즘, 수치)까지 설명한다. 이 내용은 문서에 쓰지 않는다.
2. 질문을 받는다. 다른 담당자가 답해야 하는 질문은 Open questions에 넣는다.

### 5. 쓰기

- **새로 쓰기:** `template.md`를 채워 `docs/intent/{slug}.md`에 쓴다.
- **갱신:** 대상 문서를 읽는다. 아래 차이에 닿는 부분만 고친다. 해결된 Open questions는 지우고 그 내용을 맞는 섹션으로 옮긴다. Author 줄은 그대로 둔다.
  1. `git log -1 --format=%H origin/main -- docs/intent/{slug}.md` → `<커밋>`
  2. `git diff <커밋> origin/main -- docs/prd.md docs/architecture.md server/src/nearpilot/shared/`
- **PR 수정:** 작성자가 말한 수정을 반영한다. 리뷰 의견을 반영하라고 하면 `gh pr view <번호> --comments`와 `gh api repos/{owner}/{repo}/pulls/<번호>/comments`로 읽는다. 상위 문서와 어긋나거나 새 결정이 필요한 의견은 반영하지 않는다. architecture를 고치는 docs PR이 먼저라고 작성자에게 알린다.

### 6. 검사

1. `python .claude/skills/intent/intent_tool.py check docs/intent/{slug}.md`의 위반이 0개가 될 때까지 고친다.
2. `style.md`의 점검표를 항목마다 확인한다.

### 7. 독자 시험

독자 시험은 한 번만 한다.

1. 새 컨텍스트의 서브에이전트에게 문서 파일만 준다. 서브에이전트를 쓸 수 없으면 근거를 모르는 독자가 되어 직접 답한다.
2. 아래를 그대로 묻는다. `{역할}`은 첫 번째 리뷰어의 역할이다.

   ```
   너는 NearPilot 서버 팀의 {역할} 담당이다. 이 문서의 영역은 모른다.
   이 문서만 읽고 답한다. 다른 파일은 읽지 않는다.
   1. 이 영역은 무엇을 하는가? 두 문장으로 답한다.
   2. 네가 이 영역에 주거나 받는 것은 무엇이고, 무엇을 조심해야 하는가?
   3. 뜻을 모르는 말을 모두 적는다.
   4. 지워도 네 일에 지장이 없는 문장을 모두 적는다.
   ```

3. 질문 1·2의 답이 문서의 뜻과 다르거나, 독자가 문서 안의 어긋남을 짚으면 그 부분을 고친다.
4. 질문 3의 답에 나온 말은 쉬운 말로 바꾸거나 지운다. 설명을 더하지 않는다. 단, 아래 둘은 바꾸지도 지우지도 않는다.
   - "주고받는 것" 표 맨 오른쪽 칸의 코드 이름
   - PRD 부록 A에서 이 문서가 다루는 요구사항의 한 줄 설명에 나오는 말(예: FR-07의 "안전 상태"). 근거 문서에 뜻이 있으면 처음 나올 때 괄호로 풀고, 없으면 Open questions에 적는다.
5. 질문 4의 답에 나온 문장은 지운다. 단, 아래는 남긴다.
   - 섹션과 Problem의 장면
   - Requirements에 적은 FR의 핵심 규칙
   - "주고받는 것"의 다른 상대(담당 미정 포함)에게 필요한 문장
6. 독자가 내부 방식을 묻는 답은 반영하지 않는다.
7. 6단계 검사를 다시 한다.

### 8. 작성자 교정

문서 내용은 메시지에 붙이지 않는다. 문서 파일의 절대 경로를 마크다운 링크로 주고 작성자가 직접 열어 보게 한다. 예: `[docs/intent/core-proximity.md](<저장소 절대 경로>/docs/intent/core-proximity.md)`

작성자가 말한 수정을 반영한다. `style.md`로 다듬되 뜻은 바꾸지 않는다. 고쳤으면 6단계부터 다시 한다.

### 9. PR 확인

아래를 보여주고 작성자의 확인을 받는다. PR 수정 모드는 커밋 메시지만 보여준다.

- **브랜치:** `intent/{slug}`
- **제목·커밋 메시지:** `intent({계층}): {요구사항 ID} {쉬운 말 요약}`. 예: `intent(core): FR-16·17 근접 추정`. 갱신이면 끝에 "갱신"을 붙인다.
- **리뷰어:** "주고받는 것"의 상대 담당자. 2명보다 적으면 Open questions에 적힌 담당자, 그다음 architecture §1 표의 순서로 채운다. 작성자와 담당 미정인 상대는 세지 않는다.
- **본문:** `.github/pull_request_template.md`를 채운다.
  - 주석, "해당하지 않는 묶음은 지운다." 줄, 해당 없는 체크 묶음을 지운다. 나머지 고정 문구는 그대로 둔다.
  - 확인한 것: 문서를 근거와 대조했으면 "상위 문서와 어긋나지 않는다"에 체크한다.
  - 왜: 요구사항 ID, 그리고 팀이 이 영역을 이해하고 결과물을 받아 쓰게 한다는 이유.
  - 무엇을: 섹션별 한 줄 요약.
  - 리뷰 범위: `docs/intent/` 항목에 체크한다.
  - 리뷰어에게: Open questions를 옮긴다. "보장하는 것"과 "보장하지 않는 것"을 받아 쓰는 쪽에서 확인해 달라고 쓴다.
  - 새로 쓴 문장은 `style.md`를 따른다. 점검표로 문서와 대조한다.

### 10. 커밋·push·PR

1. `git add docs/intent/{slug}.md` 후 `git commit -m "<제목>"`. 다른 파일은 스테이징하지 않는다.
2. 새로 쓰기·갱신: `git ls-remote --heads origin intent/{slug}` 결과가 있고 열린 PR이 없으면, 작성자의 확인을 받고 `git push origin --delete intent/{slug}`.
3. `git push -u origin intent/{slug}`
4. 새로 쓰기·갱신: 본문을 저장소 밖 임시 파일에 쓴다. `gh pr create --base main --head intent/{slug} --title "<제목>" --body-file <파일> --reviewer <id1>,<id2>` 후 임시 파일을 지운다.
5. `gh`를 쓸 수 없으면 push까지만 하고 제목·본문·리뷰어를 출력한다.
6. `git switch <1단계의 브랜치>`
7. PR 주소, 리뷰어, Open questions 개수를 알린다.

작성자가 중단하면 1단계의 브랜치로 돌아간다. 이번에 만든 로컬 브랜치를 지울지 묻는다.

이 문서는 `.github/ISSUE_TEMPLATE/decision.md` 양식의 이슈 초안 두 건이다. 이슈와 PR을 만들지 않았다.
두 건 모두 `specs/core-node-lab/spec.md`의 경계 밖(`server/src/`)이다. 시험 도구는 아래 동작을 바꾸지 않는다.
재현 근거는 2026-10-22 sim demo와 2026-10-23 ESP32-WROOM-32E 실측이다 (`HARDWARE_VALIDATION.md`).

## 초안 1. decision: 서버 시작 뒤 처음 발표한 기기를 실행 가능 목록에 어떻게 넣을까?

### 질문
서버가 시작된 뒤 처음 발표한 기기를 재시작 없이 재시작 복원 목록에 넣을까?

### 맥락
- 관련 영역: 상태 관리 (재시작 복원), DB (기기 발표 저장)
- 관련 요구사항: FR-04, FR-13, FR-18, FR-19
- 입력: 서버 시작 뒤 처음 보는 `node_id`의 `announce`, 그 뒤 소유자의 장소 배치·신뢰 설정과 현재 연결의 `status`
- 출력: 그 기기의 실행 가능 여부
- 바뀌는 상태: 없음. 지금은 서버를 재시작해야 실행 가능해진다
- 약속: 재시작 복원을 마치지 않은 기기는 후보가 아니다 (판정 ②, #82). 조회가 실패하면 모든 기기의 새 실행을 막는다
- 지금 정해야 하는 이유: 새 기기를 추가하면 운영 서버도 재시작해야 한다. 시험 도구는 Runtime을 정상 재시작해서 목록을 다시 읽는다 (`inventory_reloaded`)
- 관찰: 재시작 복원은 처음 한 번만 기기 목록을 읽는다. 이후 주기 실행은 이미 읽은 목록만 다시 처리한다. 새 기기의 차단 사유는 `restore_not_loaded`로 남는다

### 선택지

#### A. 주기 복원이 새 기기를 목록에 더한다
- 결과: 새 기기는 진행 중인 명령·세션·복구 건이 없다는 것을 확인한 뒤 목록에 들어간다. 그 뒤 기존 기기처럼 현재 연결 확인을 거친다. 서버를 재시작할 필요가 없다

#### B. 서버 재시작을 운영 절차로 정한다
- 결과: 코드는 바뀌지 않는다. 기기를 추가하면 서버를 재시작해야 한다. 운영 문서에 절차를 적는다

### 제안
A. 새 기기에는 복원할 실행 기록이 없다. 그래서 기존 차단 조건을 유지한 채 목록만 넓히면 된다.
B를 택하더라도 새 기기의 차단 사유를 호스트 응답과 구분해 운영자가 볼 수 있어야 한다.

## 초안 2. decision: 공용형 실행의 `reserved_at`을 어느 값으로 맞출까?

### 질문
공용형 기기 실행 문맥의 `reserved_at`을 판정 결과, 명령 연결 저장, 복원 조회에서 같은 값으로 맞추려면 어느 계층의 값을 기준으로 할까?

### 맥락
- 관련 영역: DB (원자적 예약, 명령 연결 저장), CORE (실행 문맥, 결과 인계)
- 관련 요구사항: FR-07, FR-19, NFR-03
- 입력: open 공용형 기기의 실행 요청과 기기의 `accepted`·`running`·최종 결과
- 출력: 결과 인계와 실행 상태 저장
- 바뀌는 상태: 실행 결과, `FAULT` 격리
- 약속: 같은 명령의 문맥이 바뀌면 인계를 거부한다. 결과 저장은 게이트웨이 경로에서 먼저 끝난다
- 지금 정해야 하는 이유: 실제 기기 시험에서 결과 인계마다 `CORE handover failed ... method=on_result ... error=ValueError` 경고가 반복된다. 인계 재시도가 쌓이고, 실제 실패와 경고를 구분하기 어렵다
- 관찰 (2026-10-22 sim demo, 2026-10-23 실제 기기):
  1. 공용형 예약 결과에는 `reserved_at`이 없다.
  2. 명령 연결 저장은 요청 수신 시각을 `reserved_at`으로 저장한다.
  3. 복원 조회는 저장한 값을 문맥으로 되살린다.
  4. 실행 서비스는 처음 문맥과 다른 문맥을 거부한다.

### 선택지

#### A. 공용형은 저장과 복원에서도 `reserved_at`을 비운다
- 결과: 공용형 문맥이 판정 결과와 같아진다. 대여형의 세션 시각은 그대로다

#### B. 공용형 예약 결과에도 요청 수신 시각을 넣는다
- 결과: 세 경로가 같은 시각을 쓴다. 공용형 판정 결과에 시각 필드가 하나 늘어난다

### 제안
A. 공용형은 점유 세션이 없으므로 예약 시각이 없는 쪽이 FR-19의 정의와 맞다.
어느 쪽이든 수정 뒤 실제 브로커에서 `accepted`·`running`·최종 결과를 중복 인계해도 문맥 충돌이 없는지 검증한다.
